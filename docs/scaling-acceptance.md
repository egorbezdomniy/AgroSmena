# AgroSmena CRM: итоговая приёмка

23 октября 2026. **Можно завершить итерацию и готовить ограниченный запуск.**
Блокирующих дефектов приложения в выполненных проверках не обнаружено.
Развёртывание на Linux и публичный production требуют проверок владельца ниже.
Приёмка ограничена регрессиями и короткими измерениями. Batching и новые
оптимизации не выполнялись.

## Что фактически проверено

Прочитаны stage-1, baseline, sync-read, sync-input и завершённый assignment audit;
утверждения сверены с текущими settings/env, Gunicorn config, сериализаторами,
exchange, моделями, формами, handlers и тестами. Handoff от 4 октября содержит
историческое описание DEBUG=True; текущий код использует строгий DJANGO_DEBUG
с default=False. Исторические результаты в прежних отчётах не переписаны и не
засчитываются как текущий прогон.

Среда: Windows 11 build 26200, Python 3.13.2, Django 6.0.7, DRF 3.17.1,
psycopg 3.3.5, WhiteNoise 6.12.0, PostgreSQL 16.2. В каждом запуске новый
initdb-кластер на свободном loopback-порту. verification_settings/baseline_settings
исключают dotenv **до** импорта settings, задают искусственные значения и отдельные
каталоги. Marker и SHOW data_directory защищают владение экспериментальной БД.
Схемы создавались только в этих кластерах. Production и существующие БД не читались.

Группы последовательные, лимит каждой 240 с сохранён. У catalog собственных
test-модулей не найдено; app включён в discovery группы A. Серверные проверки
подтверждают изоляцию организаций, общие/назначенные/недоступные задачи, атомарность
Task + M2M, rollback при ошибке назначений и обмена, удаление Membership/User,
ограничение переносов и защиту устаревшего выбора, конфликты и формат sync.
SnapshotTests подтвердили **<=6 SELECT именно фазы подготовки ответа**, включая
рост числа задач, nullable-связи, tombstones, удалённых и неактивных участников.
Этот бюджет не распространяется на весь HTTP-обмен.

DesktopSyncTests используют настоящие Database/SyncService/SyncRepository,
временную SQLite, HTTP live server и PostgreSQL. Проверены двусторонние изменения
клиента/сделки/задачи через сайт и desktop-службы, UUID/даты, повторный no-op,
каскады, конфликты, отказ доступа, откат и восстановление входа после открытия БД.
SQLite передаётся явным новым TemporaryDirectory-путём; AGROSMENA_DATA_ROOT
установлен verification_settings в отдельный профиль до импорта app.core.config.
SavedSyncLogin и DPAPI относятся только к искусственному токену этой SQLite.
UI и updater не запускались. Fault injection потери ответа/сети в отдельных
негативных тестах дополняет реальные успешные HTTP-обмены.

С DEBUG=False заново выполнены collectstatic, manifest-проверка всех литеральных
CSS/JS ссылок шаблонов accounts/web/catalog и реальный loopback HTTP smoke:
health 200, посторонний Host 400, landing 200, X-Request-ID, две используемые
CSS/JS ссылки 200 с immutable cache и gzip CSS. Secure cookies и явное доверие
proxy-заголовку проверены соответствующими middleware-тестами. Для специального
cleartext AuthenticatedHTTPTests cookies явно переключаются; это не проверка TLS.

`check --deploy` завершился с двумя предупреждениями:

- **W004:** HSTS=0. Включение требует работающего HTTPS и оценки поддоменов/сроков;
  предупреждение само по себе не оправдывает включение HSTS/preload.
- **W008:** SECURE_SSL_REDIRECT=False. До запуска владелец должен подтвердить
  redirect на доверенном edge либо настроить его в приложении после проверки
  схемы и отсутствия redirect loops. На loopback HTTPS отсутствует.

## Ограниченный измеренный сценарий

Согласованных требований к размеру организации, одновременным устройствам и
допустимому времени не найдено в актуальных отчётах, README и handoff. Выполнена
только техническая проверка: **400 клиентов + 300 сделок + 300 задач, 5 участников,
50 tombstones**. Общих задач 150; у выбранного сотрудника доступны 240 из 300.
Полный входящий пакет его видимости — **990 элементов: 940 live + 50 deleted**.
Изменяемый пакет меняет 10 клиентов (1% от 1 000 live CRM-записей).

Сохранены seed=20261016, anchor=2026-10-16 и существующий генератор. Он создаёт
весь прежний набор: 7 org / 19 000 live / 950 tombstones и каталог; измерялась
только small org. Остальные таблицы остаются фоном того же стенда, а не отдельными
приёмочными нагрузками. Начальный полный снимок получен до таймера.

Windows wsgiref: один процесс, bounded pool из 5 потоков, максимум **2 клиента**.
Два независимых HTTP-клиента с одной identity моделируют два устройства одной org
с одинаковой видимостью. SQLite export/import и DPAPI не входят в эти измерения;
настоящий SyncService функционально проверен отдельно. Gunicorn workers этим
экспериментом не подбирались. Перед каждой из четырёх групп — 2 успешных
последовательных прогрева, затем 6 наблюдений; при c=2 — три одновременные пары.
Прогревы записаны отдельно, в latency не включены. SQL sampling=1, HTTP/sync
diagnostics включены. Нет профилей SQL, EXPLAIN, A/B или CPU/GC-экспериментов.

**24 измеренных попытки, 0 ошибок**, ещё 8 прогревов и 2 подготовительных pull
тоже 200. Весь запуск вместе с seed/static/smoke/cleanup — 90,20 с при бюджете
300 с. HTTP-клиент сохраняет прежний timeout=45 с, настоящий desktop-клиент —
30 с; statement_timeout=25 с, lock_timeout=15 с, idle-in-transaction=30 с,
ответ <=16 MB, артефакты <=1 GB. Ни один timeout не повышался для результата.

HTTP — время клиента; server — middleware response_ready до передачи ответа.
response_prepare — сборка списка снимка, не вся JSON/HTTP-сериализация.
Удержание O — существующая наблюдаемая длительность до выхода из exchange.atomic;
acquire включает round trip/ORM и ожидание, не является чистым lock wait.
SQL duration также включает ожидание БД. При c=2 очередь executor med/max:
no-op 0,17/4,18 мс, 1% 0,22/0,32 мс. Это отделяет малую очередь HTTP-стенда
от задержки захвата O; один последовательный HTTP worker не использовался.
Тело ответа 496 516–497 195 байт. n=6 не даёт оснований публиковать p95/p99.
Разницу медиан no-op/1% нельзя трактовать как ускорение.

Конкурентные изменяемые пакеты затрагивают одни и те же 10 клиентов. Более новая
дата может примениться первой; устаревший второй пакет законно пропускается
правилом конфликтов. Поэтому SQL count одного успешного запроса равен no-op.
Это сохранённая семантика, ошибки не исключались из подсчёта ради latency.

## Проверка старых некорректных данных

`manage.py check_crm_integrity --database default` выполняет четыре COUNT в своей
PostgreSQL-транзакции **REPEATABLE READ, READ ONLY**, с statement timeout=25 с
и lock timeout=5 с. Вложенная транзакция или другой backend отвергаются.
Категории: Deal→Customer, Task→Customer, Task→Deal по organization и межорганизационные
строки Task↔Membership. Нулевые допустимые ссылки не считаются нарушением.
Подсчитываются связи, не уникальные CRM-объекты; категории могут пересекаться.
Ни имена, ни IDs/UUID, ни содержимое, SQL и параметры в вывод не входят.
При нарушениях JSON содержит числа и команда завершается кодом 1 без исправлений.

Два новых теста прошли: корректный набор с nullable-связями даёт четыре нуля;
искусственно испорченный — по одному нарушению каждой категории, сумма 4.
Сравнение строк/through до и после подтверждает отсутствие изменений.
На полном синтетическом baseline seed команда также вернула четыре нуля.

**Перед использованием существующей БД её владелец должен отдельно выполнить
проверку в разрешённом окружении.** Здесь она на существующих БД не запускалась.
Для этого нужны явно выбранные settings/DB и конфигурация процесса с
DJANGO_LOAD_DOTENV=false до импорта; рекомендуются права DB только на чтение.
Действующий .env и реальные параметры в эти инструкции/артефакты не включены.
Команда не проверяет и не исправляет все возможные виды повреждений данных.

## Недоступное и обязательные условия первого запуска

Linux отсутствует: `wsl --list --verbose` возвращает 1 и сообщение о неустановленной
подсистеме; docker/podman в PATH нет, другой изолированный Linux-стенд не предоставлен.
Ничего не устанавливалось и не разворачивалось. **Gunicorn startup не проверен.**
Отдельного TLS/reverse-proxy стенда нет; loopback HTTP и unit-тест заголовка
не подтверждают TLS, edge rate limits или реальную цепочку доверенных proxy.

Обязательное перед доступом пользователей к ограниченному окружению:

1. На выбранном Linux-релизе выполнить startup Gunicorn с DEBUG=False, collectstatic,
   health/static/auth/CRUD/assignments/member-delete и headless SyncService smoke.
   Проверить схему БД и release command. До этого развёртывание остаётся условным.
2. Использовать отдельное ограниченное окружение с закрытым доступом и малыми org
   в измеренном диапазоне; не расширять его на большой полный sync по этому отчёту.
   Консервативные одна реплика/один worker не являются измеренной конфигурацией ёмкости.
   LocMem throttle не даёт общего строгого лимита workers/реплик и теряет историю
   при перезапуске. Для публичного входа обязательна подтверждённая общая защита
   login endpoints; несколько workers без неё этим этапом не одобряются.
3. Владелец задаёт секреты и явные hosts/origins через разрешённое окружение,
   сохраняет действующий корректный SECRET_KEY, проверяет DB TLS по требованиям
   среды. Secure cookies остаются включёнными для HTTPS. Trust proxy/XFF hops,
   redirect и HSTS настраиваются только после проверки фактического edge.
4. Сохранить Gunicorn timeout=30 и desktop timeout=30 до отдельного обоснования.
   Проверить полный путь с очередью и proxy на выбранном релизе; Windows-результат
   максимум 4,002 с не является гарантией Linux. Прежние отказы больших конкурентных
   обменов и причина прежнего замедления large остаются открытыми; они не проверялись
   заново и не снимаются этим малым сценарием. Вход всё ещё делает отдельные
   конфликтные SELECT; для неограниченного объёма подтверждения нет.
5. До старта сохранить прежние source/release, настройки, статику и проверенную
   резервную копию используемой БД. Заранее определить возврат релиза и закрытие
   доступа при 5xx/worker kill/ошибке целостности; потерянный ответ не доказывает
   rollback уже закоммиченного sync. Восстановление данных — отдельное решение
   владельца с учётом записей после backup. Миграции/restore в существующей БД
   этой приёмкой не выполнялись. Перед её использованием нужна read-only проверка выше.
