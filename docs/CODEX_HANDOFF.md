## 2. Архитектура и данные

```text
Desktop: PySide6 → Services → Repositories → SQLAlchemy → SQLite
                                              ↕ ручной REST sync
Сайт: Django Templates + Forms → Views → Models → PostgreSQL
Обновления Windows: HTTPS-каталог/ZIP → отдельный updater → файлы сборки
```

Desktop работает офлайн. Сервер использует Django, DRF и PostgreSQL; сайт работает с серверными моделями. UI desktop обращается к данным через сервисы. Alembic обслуживает SQLite, Django migrations — PostgreSQL.

Основные записи имеют числовой ID, UUID и даты создания/изменения. Между устройствами связи сопоставляются по UUID; локальные ID могут отличаться от серверных.

| Сущность | Основные поля |
| --- | --- |
| Customer | Имя, компания, телефон, email, Telegram, должность, заметки |
| Deal | Название, обязательный клиент, сумма, стадия, описание, ожидаемая дата закрытия |
| Task | Название, описание, необязательные клиент/сделка/срок, приоритет, статус, назначенные сотрудники |

Стадии сделки: Новая, Контакт, Предложение, Переговоры, Успешно, Проиграна. Приоритеты задач: Низкий, Обычный, Высокий. Статусы: Новая, В работе, Выполнена, Отменена. Пустая сумма сделки сохраняется как ноль; отрицательная запрещена. Удаление клиента удаляет его сделки, задачи сохраняются с очищенными связями.

### Организации и права

- Customer, Deal и Task обязательно принадлежат Organization. Организация определяется текущим пользователем; входным идентификаторам организации доверять нельзя. Связи с чужими организациями запрещены.
- Пользователь состоит максимум в одной организации через `Membership.user` (OneToOne). Роли: `admin`, `supervisor`, `manager`. Все имеют CRM CRUD в своей организации, только `admin` управляет участниками и каталогом товаров.
- Удаление участника удаляет членство, не аккаунт и не CRM-записи. Последнего активного администратора нельзя удалить/понизить.
- Django superuser и администратор организации — разные права. `/admin/` и публикация установщиков предназначены для системных суперпользователей.
- Обычный REST использует session authentication. Общие серверные модели проверяют связи и блокируют организацию при сохранении; прямой SQL/`QuerySet.update()` требуют отдельного учёта этих правил и синхронизации.
- Старые серверные данные сохранены миграцией в организации «Данные до v0.5»; доступ к ней автоматически не назначается.

### Назначения задач

На сервере `Task.assignees` — M2M с Membership; пустой список означает «Все сотрудники». `visible_tasks()` ограничивает дашборд, списки, карточки, связанные задачи, смену статуса и API общими задачами и задачами текущего участника.

Desktop хранит `assignee_usernames` как JSON, список сотрудников — в `SavedSyncLogin.members_json`. Диалог содержит «Все сотрудники» и множественный выбор. `TaskService` и `DashboardService` учитывают текущий серверный логин; без входа видны только общие задачи. Назначения передаются в sync как `assignee_usernames`; сервер проверяет активное членство в той же организации. Список сотрудников обновляется при входе и обмене.

## 5. Ручная синхронизация

`/api/sync/login/` выдаёт подписанный Django-токен на 12 часов (не JWT). Проверяются активность, членство, организация и состояние пароля; вход ограничен 10 запросами/минуту/IP. Desktop хранит токен под Windows DPAPI, пароль не сохраняет. HTTPS обязателен, HTTP разрешён только для loopback; redirects клиента запрещены.

Первый обмен требует подтверждения привязки SQLite к серверу/организации. Привязка сохраняется до сетевого обмена. Desktop отправляет полный локальный снимок и tombstones на `/api/sync/exchange/`; сервер объединяет записи по UUID в транзакции под блокировкой организации. Более новый `updated_at` побеждает, при равенстве — сервер; допустимое отклонение в будущее 5 минут. Лимит входного пакета — 10 000 записей.

Сервер возвращает снимок организации с задачами, доступными текущему участнику, и список сотрудников. Более новое изменение уже недоступной задачи отклоняет обмен. Desktop импортирует клиентов → сделки → задачи и удаления, обновляет `last_sync_at` только после успешной транзакции. Формат: `entity`, `uuid`, даты, `deleted`, `fields`; связи — `customer_uuid`/`deal_uuid`.

Обмен удерживает SQLite `BEGIN IMMEDIATE`, включая сетевой этап. Автоматической синхронизации, курсорных дельт и UI разрешения конфликтов нет. Выход удаляет сохранённый токен, но не локальные данные и привязку организации.

## 6. Полные установщики и патч-обновления

**Полный установщик:** `/download/` и `/download/installer/` публичны. `/release-admin/` доступен только активным superuser, позволяет загрузить EXE до 512 МБ и опубликовать версию/описание. Проверяются расширение, размер и MZ; цифровой подписи нет. Подробности: `docs/downloads.md`.

`APP_INSTALLER_DIR` по умолчанию указывает на `crmserver/releases/installers/`. Случайное имя EXE и атомарный `current.json` определяют текущую версию. Каталог исключён из Git: сам Git-деплой не переносит установщик. На Render нужно постоянное хранилище и загрузка через админку либо отдельный перенос файлов. При нескольких экземплярах требуется общее хранилище. Сообщение «Установщик пока не опубликован» обычно означает отсутствие корректного файла/манифеста в этом окружении. По журналу в `docs/downloads.md` последняя локальная сборка — установщик 0.1.2 от 19.09.2026; актуальная публикация на хостинге не проверялась.

**Патчи:** `/api/app/update/` публично выдаёт статический JSON. Подробный протокол, выпуск и восстановление описаны в `docs/updates.md`; здесь его не дублировать. Публикация полного установщика не меняет каталог патчей.

Ключевые ограничения: применять патчи можно только в установленной сборке; нужен полный путь версий и точные исходные onedir-артефакты. Проверяются HTTPS, SHA-256, старые/новые файлы и безопасные пути ZIP. Внешний updater ждёт закрытия CRM, сохраняет файлы и snapshot SQLite, применяет изменения, запускает проверку с Alembic и при ошибке откатывает всю цепочку. Журнал позволяет восстановиться после аварии. Основной процесс CRM файлы установки не заменяет. `mandatory` не запрещает офлайн-работу; подписи релизов и автоматической очистки backup нет. Реальные патчи в текущем каталоге отсутствуют.

Для сборки использовать существующие requirements и `installer/build.ps1`; ключ `-SkipSmokeTest` пропускает запуск собранной CRM. Предыдущая сборка не содержит последующих изменений исходников автоматически.

## 7. Конфигурация, хранение и миграции

Desktop-профиль: `%LOCALAPPDATA%/AgroSmenaCRM/` — `data/crm.db`, настройки, логи, sync-токен и `updates/` с загрузками, runners, backup и журналом. Установка: `%LOCALAPPDATA%/Programs/AgroSmenaCRM/`. `AGROSMENA_DATA_ROOT` переопределяет профиль; без него исходники и установленная CRM используют одну базу. Старый проектный `data/crm.db` переносится backup API только при отсутствии целевой базы.

`Database.create_tables()` применяет Alembic head. Baseline `0001_baseline` не переписывать; новые изменения — отдельными ревизиями. `0002_task_assignees` добавляет назначения и кэш сотрудников. SQLite мигрируется при старте новой desktop-сборки.

Сервер читает `crmserver/.env`; переменные процесса имеют приоритет. Настройки: `DJANGO_SECRET_KEY`, `DJANGO_ALLOWED_HOSTS`, `POSTGRES_DB/USER/PASSWORD/HOST/PORT`, `APP_UPDATE_CATALOG`, `APP_INSTALLER_DIR`. PostgreSQL обязателен, timeout подключения 5 секунд, timezone UTC. **В текущем коде `DEBUG = True` задан напрямую; `DJANGO_DEBUG` не используется.** `agrosmena.onrender.com` добавлен в allowed hosts. Desktop URL патчей задаётся отдельно от sync через `AGROSMENA_UPDATE_URL`.

Серверные миграции, важные для последних изменений:

| Миграция | Назначение / известное состояние |
| --- | --- |
| `tasks/0004_task_assignees` | M2M назначений; успешно применена к подключённой локальной базе 27.09.2026 при исправлении `/dashboard/` |
| `catalog/0001_initial` | Каталоги, типы, характеристики, товары; в рамках разработки не применялась |
| `catalog/0002_storefront_logo` | Логотип каталога; в рамках разработки не применялась |

Текущее состояние баз и хостинга не проверено: пользователь мог применить миграции самостоятельно. Перед использованием новой схемы нужны соответствующие Django migrations, при деплое — обновление собранной статики. Ошибка `relation ... does not exist` указывает на отсутствующую таблицу/неприменённую миграцию; не маскировать её отключением фильтрации доступа. `connection timeout expired` — повод проверить PostgreSQL и host/port. Локальный вспомогательный кластер обслуживает `crmserver/tools/local_postgres.py` (порт разработки 55432).

## 8. Документация и проверки

`README.md` и `crmserver/README.md` содержат общие инструкции, но местами исторические формулировки. При противоречии ориентироваться на текущий код. Подробности обновлений/скачиваний — `docs/updates.md`, `docs/downloads.md`.

Существующие desktop-тесты находятся в `tests/` (сервисы, Qt UI, sync, обновления и opt-in проверка сборок). Серверные — в `crmserver/{crmserver,accounts,web,synchronization}/`. Отдельного набора тестов каталога пока нет. Наличие старых тестов и прежних успешных прогонов не означает проверку новых назначений, каталога или актуальной сборки. При обновлении этого документа 04.10.2026 выполнено только чтение исходников и редактирование документации.
