Этот файл описывает существующую реализацию, а не новый запрос на разработку. Перед изменениями сверять соответствующие участки кода: документ со временем может устареть. Не запускать обновление, миграцию рабочей базы или публикацию автоматически только потому, что здесь приведены команды.

## 1. Краткий итог

Проект содержит три связанных части:

- Desktop CRM: Python, PySide6, SQLAlchemy, локальная SQLite; приложение сохраняет возможность работы без сервера.
- Сервер: Django, Django REST Framework, PostgreSQL, пользователи и организации, изолированные данные организаций.
- Сайт: Django Templates, Django Forms, CSS и немного JavaScript; работает с теми же серверными моделями.

Реализованы клиенты, сделки, задачи, подробные карточки, Dashboard, CRUD, поиск/фильтры, ручная двусторонняя синхронизация desktop с сервером и файловые патч-обновления Windows-приложения с отдельным updater, откатом и Alembic для SQLite. Последние изменения — единая бело-тёмно-зелёная тема сайта и desktop, фоновые анимации, упрощение sidebar и быстрая смена стадии сделки; подробности в разделе 15.

Исторические названия запросов пользователя: v0.1 — desktop, v0.3 — backend, v0.4 — сайт, v0.5 — пользователи/организации. Это **не текущая версия сборки**. В `version.json` теперь `0.1.1`; серверный каталог остаётся на `0.1.0` с пустым списком патчей. Новая версия не публиковалась на сервер. Версии `0.8.1`, `0.8.2`, `0.8.3` в документации — примеры.

Предыдущий запрос на систему обновлений завершён. Эта передача контекста не означает, что нужно повторно реализовывать обновления.

- Не включать в ответы и документацию `.env`, пароли, токены или содержимое пользовательской базы.

## 3. Архитектура и основные правила

```text
Desktop: PySide6 UI → Services → Repositories → SQLAlchemy → SQLite
                                      SQLite ↔ REST sync API ↔ Django/PostgreSQL
Сайт:    Templates + Forms → Django Views → Django Models → PostgreSQL
Updates: UpdateService → HTTPS-каталог и ZIP → отдельный updater.exe → файлы сборки
```

- Desktop UI не должен напрямую обращаться к базе.
- Локальные и серверные числовые ID могут отличаться. Между устройствами записи и связи сопоставляются по UUID.
- На сервере Customer, Deal, Task обязательно принадлежат Organization.
- Организация определяется по текущему пользователю, а не доверяется входным данным клиента.
- Связи сделки/задачи не могут указывать на объекты другой организации.
- Alembic обслуживает desktop SQLite; Django migrations — серверную PostgreSQL. Это разные системы миграций.
- Основной процесс CRM не заменяет файлы установленного приложения. Это делает только отдельный updater после закрытия CRM.

## 4. Сущности

Общие поля основных записей: `id`, `uuid`, `created_at`, `updated_at`.

| Сущность | Поля |
| --- | --- |
| Customer | `name`, `company_name`, `phone`, `email`, `telegram`, `position`, `notes` |
| Deal | `title`, обязательный `customer_id`, `amount`, `stage`, `description`, необязательный `expected_close_date` |
| Task | `title`, `description`, необязательные `customer_id`, `deal_id`, `due_date`, `priority`, `status` |

Стадии сделки: Новая, Контакт, Предложение, Переговоры, Успешно, Проиграна.

Приоритеты задач: Низкий, Обычный, Высокий. Статусы: Новая, В работе, Выполнена, Отменена.

Имя клиента и названия сделки/задачи обязательны; сумма сделки неотрицательна. Удаление клиента каскадно удаляет его сделки. Задачи сохраняются с очищенными удалёнными связями.

### Пользователи, организации и права

- Один пользователь связан максимум с одной организацией через `Membership.user` (OneToOne).
- Роли: `admin` — Администратор, `supervisor` — Руководитель, `manager` — Менеджер.
- Администратор организации управляет участниками и ролями. Руководитель и менеджер сейчас имеют одинаковые права на CRM CRUD, но не на управление пользователями.
- Администратор организации не равен Django superuser/is_staff. Глобальный Django Admin предназначен для системного суперпользователя.
- Удаление участника удаляет членство, но не аккаунт и не CRM-записи. Последнего активного администратора нельзя убрать/понизить.
- Старые серверные данные миграция сохраняет в организации «Данные до v0.5». Автоматически раздавать доступ к ней нельзя: доверенного участника назначает системный администратор.
- Обычный REST использует session authentication и проверки входа/организации. UUID и временные поля обычных serializers доступны только для чтения.
- Прямой SQL и `QuerySet.update()` обходят часть проверок `save()`/signals. Не использовать их для бизнес-изменений без отдельного учёта tenant-проверок и синхронизации.

## 8. Ручная синхронизация данных

### Файлы сервера

- `synchronization/auth.py`: подписанные Django-токены desktop, срок 12 часов; это не JWT. Проверяются активность пользователя, актуальное членство, организация и hash состояния пароля.
- `synchronization/views.py`: вход и обмен; ограничение частоты входа 10 запросов/минуту/IP.
- `synchronization/serializers.py`: формат записей/полей обмена.
- `synchronization/services.py`: UUID-сопоставление, LWW-конфликты, связи и транзакция под блокировкой организации.
- `synchronization/models.py`, `signals.py`, `apps.py`: tombstones удалений, включая удаления через сайт/API/admin.
- `synchronization/urls.py`, `migrations/0001_initial.py`: маршруты и схема.

### Алгоритм и ограничения

1. Desktop входит через `/api/sync/login/`. Пароль не сохраняется; токен в SQLite защищается Windows DPAPI текущего пользователя.
2. Первая синхронизация требует подтверждения привязки SQLite к серверу и организации. Привязка сохраняется **до** сетевого обмена, чтобы потеря ответа не позволяла перепривязать те же данные другому tenant.
3. Desktop отправляет полный снимок локальных сущностей и удалений на `/api/sync/exchange/`.
4. Сервер объединяет изменения по UUID: более новый `updated_at` побеждает; при равных временах побеждает сервер. Изменения слишком далеко в будущем отклоняются (допуск 5 минут).
5. Сервер возвращает полный объединённый снимок. Desktop импортирует клиентов → сделки → задачи, применяет удаления, обновляет tombstones и `last_sync_at` только при успешной транзакции.

Формат записи включает `entity`, `uuid`, `created_at`, `updated_at`, `deleted`, `fields`. Связи передаются как `customer_uuid`/`deal_uuid`. Обмен ограничен 10 000 записями.

В локальном обмене используется `BEGIN IMMEDIATE`, включая сетевой этап: это защищает снимок от параллельной записи, но удерживает SQLite write lock на время запроса. Автоматического сложного offline-sync, курсорных дельт и интерфейса разрешения конфликтов нет. Хранение времени последней синхронизации не означает, что передаются только изменения после него.

HTTP разрешён только для loopback при разработке; удалённый сервер требует HTTPS. Redirects sync-клиента запрещены. Выход не удаляет локальные бизнес-данные и не отвязывает базу от организации. Закрытие приложения может сохранять вход, явный выход удаляет сохранённый токен.

## 9. Файловые обновления приложения

### Протокол и безопасность

- `/api/app/update/` публичен специально: возвращает release metadata, а не данные организаций. Читает статический JSON, не требует серверной миграции. Некорректный/отсутствующий каталог даёт 503.
- Каталог: `latest_version`, `patches`, `mandatory`, `release_notes`. Патч: `from_version`, `to_version`, HTTPS `url`, `sha256`, необязательные notes/mandatory.
- ZIP содержит `manifest.json` и только добавленные/изменённые файлы. Действия: `add`, `replace`, `delete`. Для replace/delete дополнительно требуется `old_sha256` — проверка точной исходной сборки.
- Выбирается цепочка с минимальным числом патчей до последней версии. Downgrade запрещён. Без полной цепочки нужен установщик.
- Проверяются SHA архива, исходных и новых файлов, пути и содержимое ZIP. Запрещены traversal, Windows device/ADS-пути, ссылки/junction, неожиданные/дублирующиеся записи, пользовательские данные.
- Есть лимиты размеров: архив 2 GiB, распакованные данные 8 GiB, 30 000 entries, manifest 8 MiB, каталог 2 MiB, до 1000 связей патчей.
- Для обновлений HTTPS обязателен даже локально, стандартная TLS-проверка не отключается, HTTPS→HTTP redirect запрещён.
- Это дельты **на уровне файлов**, не байтовые бинарные дельты. Если изменился EXE/DLL, он скачивается целиком. Неизменившиеся файлы не скачиваются.

### Установка, проверка и откат

1. UpdateService загружает/проверяет ZIP в фоне и копирует updater в пользовательский профиль вне папки установки.
2. CRM запускает внешний updater и закрывается. Updater ждёт PID (до 120 секунд) и берёт общую блокировку.
3. До изменений проверяются исходные хеши/вся цепочка/свободное место, сохраняются резервные копии файлов, версии и snapshot SQLite, пишется долговечный журнал.
4. Файлы заменяются атомарно, патчи применяются последовательно, проверяются итоговые SHA.
5. Новая CRM запускается с `--update-verify`: выполняет Alembic upgrade, создаёт UI и завершается. Режим разрешён только для ожидаемой фазы журнала с соответствующим probe token.
6. При успехе транзакция фиксируется и запускается обычная CRM. При ошибке возвращаются исходные файлы, версия и snapshot SQLite всей цепочки.

Откат БД выполняется snapshot, а не опасным downgrade. Он безопасен при отсутствии сторонних писателей в SQLite; внешние редакторы базы нужно закрыть. Будущие миграции не должны иметь внешних побочных эффектов, которые snapshot не отменит.

После аварийного завершения следующий старт обнаруживает журнал и запускает восстановление. Если сам EXE не стартует, путь независимого runner/плана находится в `updates/recovery.json`. При повреждённом backup или заблокированном восстановлении журнал сохраняется и повреждённая CRM не запускается. После успешного отката вследствие ошибки обычный запуск выполняет пользователь вручную.

### Что пока не сделано / не обещать

- Каталог сейчас пуст: production HTTPS-хостинг, сертификаты и реальные ZIP URL не настроены этой реализацией.
- Старые сборки без updater требуют одной полной установки новой версии.
- Из исходников установка файловых патчей выключена, хотя проверка/загрузка доступны.
- `mandatory` показывается в UI, но не блокирует офлайн-работу принудительно.
- Нет цифровой подписи релизов/установщика; реализованы доверенный HTTPS и SHA-256.
- Backup и логи автоматически не чистятся.
- Не поддержаны переименования только регистром и переход файл↔каталог.
- Генерировать патчи нужно по точным сохранённым onedir-сборкам, не по папкам исходников и не по повторной произвольной сборке «той же версии».

## 10. Хранение, конфигурация и миграции

Установленные файлы: `%LOCALAPPDATA%/Programs/AgroSmenaCRM/`.

Пользовательский профиль по умолчанию, **включая запуск из исходников**:

```text
%LOCALAPPDATA%/AgroSmenaCRM/
  data/crm.db                 # бизнес-данные, состояние sync, DPAPI-токен
  settings/updates.json       # URL каталога
  logs/crm.log
  logs/updater.log
  logs/update-startup.log
  runtime.lock
  updates/downloads/
  updates/runners/
  updates/backups/
  updates/transaction.json    # только незавершённая транзакция
  updates/recovery.json
  updates/last-result.json
```

`AGROSMENA_DATA_ROOT` переопределяет пользовательский профиль. Для безопасного экспериментального запуска задавать отдельный профиль **вне папки установки**. Без override исходники и установленная CRM используют одну и ту же SQLite.

Прежний `data/crm.db` в проекте при первом старте копируется SQLite backup API, только если целевой базы ещё нет. Исходная база сохраняется, существующая целевая не перезаписывается.

`Database.create_tables()` теперь запускает Alembic upgrade head, а не просто `metadata.create_all`. Baseline содержит фиксированную схему и проверяет совместимость существующих таблиц. Новые изменения схемы оформлять новыми ревизиями; baseline не переписывать. Разрушительный downgrade baseline намеренно запрещён.

Сервер читает `crmserver/.env` через python-dotenv, переменные процесса имеют приоритет. Основные параметры: `DJANGO_SECRET_KEY`, `DJANGO_DEBUG`, `DJANGO_ALLOWED_HOSTS`, `POSTGRES_DB`, `POSTGRES_USER`, `POSTGRES_PASSWORD`, `POSTGRES_HOST`, `POSTGRES_PORT`. PostgreSQL обязателен, автоматического перехода на SQLite нет. Connect timeout — 5 секунд. Язык русский, timezone UTC.

`APP_UPDATE_CATALOG` задаёт серверный путь JSON-каталога. `AGROSMENA_UPDATE_URL` задаёт desktop HTTPS URL каталога. Адрес sync-сервера и адрес каталога обновлений — разные настройки.

Предыдущая ошибка `OperationalError: connection timeout expired` относилась к недоступности PostgreSQL. При повторении сначала проверять службу/локальный кластер и host/port, а не менять модели или подменять backend SQLite. Скрипт `local_postgres.py` поддерживает локальный кластер `.postgres` (порт разработки 55432); init — отдельная операция настройки, не выполнять поверх существующей конфигурации вслепую.
