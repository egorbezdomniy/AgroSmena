# Обновления Windows CRM

## Где что находится

- `version.json` — SemVer текущей сборки (начальная версия `0.1.0`).
- `updatekit/protocol.py` — формат, цепочки SemVer, хеши, проверка ZIP и путей.
- `app/services/update_service.py` — HTTPS-каталог, загрузка, прогресс, подготовка отдельного updater.
- `app/ui/pages/updates_page.py` — Настройки → Обновления, фоновые QThread.
- `updater.py`, `updatekit/engine.py`, `updatekit/locking.py` — внешний процесс, ожидание CRM, блокировка, backup, применение, откат и запуск.
- `Updater.spec`, `AgroSmena.spec`, `installer/build.ps1` — сборка updater.exe и установщика.
- `migrations/`, `alembic.ini`, `app/core/migrations.py` — версионирование SQLite.
- `crmserver/crmserver/app_updates.py` — публичный, не зависящий от организаций API каталога.
- `tools/create_patch.py` — генератор ZIP и метаданных публикации.

## Хранение

Программа: `%LOCALAPPDATA%/Programs/AgroSmenaCRM/`.
Пользовательский профиль: `%LOCALAPPDATA%/AgroSmenaCRM/`:

```text
data/crm.db                 # CRM, привязка организации, защищённый токен
settings/updates.json       # HTTPS адрес каталога
logs/crm.log
logs/updater.log
logs/update-startup.log
updates/downloads/         # ZIP с проверенным SHA-256
updates/runners/           # копия standalone updater.exe вне устанавливаемых файлов
updates/backups/           # файлы предыдущей версии и SQLite snapshot
updates/transaction.json   # существует только пока транзакция не завершена
updates/recovery.json      # путь к независимому updater и его плану
updates/last-result.json    # результат для страницы настроек
```

Источники тоже используют пользовательский профиль. При первом запуске, только если
целевой SQLite ещё нет, прежний `data/crm.db` копируется SQLite backup API; оригинал
остаётся на месте. Если целевая база уже существует, она не перезаписывается.
Для изолированной разработки/тестов задайте `AGROSMENA_DATA_ROOT` вне папки приложения.
Установка патчей из исходников отключена; проверка каталога и загрузка доступны.

## Сборка и выпуск

Старая версия без updater требует однократной установки нового полного установщика.
Обычные дальнейшие обновления используют патчи. Перед первым выпуском проверьте
`version.json` и сохраните точную эталонную папку onedir: нельзя повторно собирать
«ту же версию» и считать её тем же основанием патча.

```powershell
.\.venv\Scripts\python.exe -m pip install -r requirements-build.txt
powershell -ExecutionPolicy Bypass -File installer\build.ps1
```

Результат: `dist/AgroSmenaCRM/`, отдельный `dist/updater.exe`, NSIS-установщик.
Для каждой версии меняйте `version.json`, сохраняйте предыдущую сборку отдельно и
собирайте новую. Скрипт берёт имя/метаданные NSIS из того же `version.json`.

```powershell
python tools/create_patch.py old_build/ new_build/ 0.8.1 0.8.2
# или
python tools/create_patch.py old_build/ new_build/ 0.8.1 0.8.2 --output dist/patches/0.8.1-0.8.2.zip
```

Получаются ZIP, `.manifest.json` и `.release.json`. ZIP содержит только изменённые
и добавленные файлы и manifest; удаления представлены только в manifest. Исходные
деревья не меняются, существующий ZIP не перезаписывается. `version.json` управляется
updater отдельно. Для replace/delete `old_sha256` обязателен: это защита от неправильной
базовой сборки. Symlink/junction, пользовательские БД/логи/настройки и опасные Windows
пути запрещены. Переименования только регистром и переход файл↔директория не поддержаны.

Это файловые, не бинарные дельта-патчи: изменившийся EXE/DLL скачивается целиком,
неизменившиеся Qt/Python DLL и остальные файлы не скачиваются. Нельзя сравнивать
папки Python-исходников вместо реальных onedir-сборок.

## Публикация на Django

GET `/api/app/update/` возвращает каталог из `crmserver/releases/catalog.json`.
Другой путь задаётся `APP_UPDATE_CATALOG`. Каталог не требует входа, не читает CRM-БД
и не раскрывает данные организаций; REST API клиентов/сделок/задач сохраняет свою защиту.
Новых серверных моделей и миграций для статического каталога не требуется.

1. Разместите готовые ZIP на своём HTTPS-хранилище/CDN.
2. Заполните реальные HTTPS URL в `.release.json` и перенесите записи в `patches` каталога.
3. Укажите `latest_version`, `mandatory`, `release_notes` на уровне каталога.
   У каждого патча также поддерживаются `mandatory` и `release_notes`.
4. Сначала публикуйте ZIP, потом атомарно заменяйте каталог. Старые патчи сохраняйте,
   пока нужны обновления с соответствующих версий.
5. Настройте HTTPS перед Django и задайте desktop URL в «Настройки → Обновления»
   или `AGROSMENA_UPDATE_URL=https://ваш-домен/api/app/update/`.

Обычный `http://127.0.0.1:8000` не подходит для клиента обновлений. Обход проверки
TLS отсутствует; HTTPS→HTTP редирект запрещён ещё до запроса. В репозитории нет
выдуманных production URL или сертификатов. Начальный каталог содержит пустой список.

`mandatory` явно отмечается в UI; автоматическое принудительное закрытие приложения
и запрет офлайн-работы не включены. Выбор цепочки — минимальное число последовательных
патчей до последней версии, без downgrade. При отсутствии полной цепочки отображается
сообщение о необходимости установщика. Notes отображаются как обычный текст.

## Транзакция и SQLite

Updater копируется из установленного standalone EXE в профиль пользователя, запускается
и ждёт PID CRM. Основной процесс не меняет установленные файлы. Общая OS-блокировка
запрещает другую CRM, пока updater работает. Хеш архива, manifest, исходные и новые файлы
проверяются. Backup и атомарный журнал сохраняются до первой замены.

После всей цепочки новая CRM запускается отдельным проверочным процессом с
`--update-verify`: выполняет `alembic upgrade head` программно, создаёт все страницы
интерфейса и завершается. Только при коде 0 обновление фиксируется и CRM запускается
обычным образом. Таймаут проверки — 120 секунд; перед откатом updater завершает
проверочный процесс и ждёт освобождения файлов.

Ошибка применения/миграции откатывает все патчи цепочки целиком, восстанавливает
исходный `version.json` и предмиграционный snapshot SQLite. Обратные миграции с
потенциальной потерей данных не запускаются. Это безопасно, пока никто снаружи CRM
не пишет в эту БД: приложения соблюдают OS-lock, внешние SQLite-редакторы нужно закрыть.
Не запускайте миграции с внешними побочными эффектами (сеть/файлы вне SQLite).

При аварийном завершении updater следующий запуск CRM обнаружит журнал и передаст
восстановление сохранённому updater. Если повреждён сам EXE и он не запускается,
запустите вручную сохранённый runner из `updates/recovery.json`:

```powershell
& 'путь-к-сохранённому-updater.exe' --plan 'путь-к-plan.json' --recover
```

Если backup повреждён или файл по-прежнему заблокирован, журнал сохраняется,
повреждённая версия не запускается. Устраните блокировку и повторите восстановление.
Backup/логи не удаляются автоматически. После неудачного обновления с успешным откатом
запустите CRM вручную: страница обновлений покажет причину. Ошибка обычного перезапуска
после успешной проверки пишется в лог; проверенная установленная версия сохраняется.

Будущие изменения схемы создавайте отдельными ревизиями, не редактируйте baseline:

```powershell
python -m alembic revision --autogenerate -m "describe change"
python -m alembic upgrade head
```

Baseline содержит фиксированную схему, принимает совместимую прежнюю SQLite без
удаления записей. Сначала проверяйте новую миграцию на копии реальной базы.
API Alembic применяется по [официальной рекомендации](https://alembic.sqlalchemy.org/en/latest/cookbook.html#sharing-a-connection-across-one-or-more-programmatic-migration-commands).

## Проверки

```powershell
python -m unittest tests.test_updates tests.test_updates_ui -v
cd crmserver
python manage.py test crmserver.test_app_updates -v 2
cd ..
$env:AGROSMENA_TEST_BUILD=(Resolve-Path dist/AgroSmenaCRM).Path
python -m unittest tests.test_update_build -v
```

Первые проверки покрывают цепочки, SHA, повреждённый ZIP, ошибки файлов, настоящий
Windows file lock, journal recovery, порчу backup, изоляцию путей, HTTPS и SQLite.
Последний тест копирует настоящую сборку во временные каталоги, применяет ZIP отдельным
updater.exe, проверяет миграцию и обычный перезапуск CRM, затем намеренно ломает миграцию
и проверяет откат БД/файлов. Рабочий профиль и БД пользователя не используются.
