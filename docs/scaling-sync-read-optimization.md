# AgroSmena CRM: чтение исходящего sync-снимка

Дата проверки: 22 октября 2026. Исходный `scaling-baseline.md` и результаты
16 октября сохранены. Эта итерация касается только чтения ответа; входное разрешение
конфликтов, сохранение моделей, сигналы, транзакция и блокировка организации сохранены.

Подготовка снимка сокращена с **247 / 1 207 / 2 167 до 6 SELECT** для трёх масштабов.
88 тестов прошли. В дополнительной контрольной паре первичная загрузка large дала
HTTP 7,05 → 4,21 с и peak working set 115,3 → 101,3 MiB. Ускорение всего обмена с
полным входящим пакетом не подтверждено: есть ухудшившиеся серии и сохраняются
отказы при пяти конкурентных pull крупной организации. Подробности и границы
сравнений приведены ниже.

## Причины SQL

Профили отдельного настоящего HTTP-запроса подтверждают следующее разбиение
**полного обмена без правок**, включая входящие tombstones:

| Источник | 1 000 | 5 000 | 9 000 | Изменение этой итерации |
| --- | ---: | ---: | ---: | --- |
| Вход: поиск живой записи `select_for_update` по UUID | 990 | 4 950 | 8 910 | Без изменений |
| Вход: поиск tombstone по entity/UUID | 990 | 4 950 | 8 910 | Без изменений |
| Ответ: клиенты, сделки с клиентом, доступные задачи со связями | 3 | 3 | 3 | PK/UUID вместо полных связанных строк |
| Ответ: исходный prefetch memberships, затем users | 2 | 2 | 2 | Один упорядоченный JOIN-prefetch |
| Ответ: `order_by().values_list()` исполнителей внутри сериализатора | 240 | 1 200 | 2 160 | Устранён, используется подготовленный список |
| Ответ: tombstones и справочник активных сотрудников | 2 | 2 | 2 | Справочник читает только необходимые поля |
| Вне ответа/применения: auth user, два membership lookup, org lock, проверка членства | 5 | 5 | 5 | Без изменений |
| Всего до | **2 232** | **11 112** | **19 992** | |

Загрузка UUID связей уже использовала `select_related`: самостоятельного N+1
клиентов/сделок в этой фазе не было. DRF читает FK ID без отдельного запроса;
`serialize_record` затем берёт UUID из присоединённой строки. Конструктор
`OrganizationSerializer` на выходе не получает request и не делает membership lookup
для каждой строки. Два lookup выше относятся к auth/permissions всего HTTP-запроса.
`sync_record_counts` проходит готовый список в памяти, без SQL.

Первичный пустой пакет не имеет входных конфликтных чтений. Пакет с изменениями
1% клиентов имеет дополнительные входные SQL сохранения, savepoint и обновления
дат; их нельзя приписывать исходящему N+1.

## Изменения

- `crmserver/synchronization/services.py`: только выборки в существующей фазе
  `response_prepare_ms`; `Prefetch` исполнителей с `select_related('user')`, порядком
  `user__username` и отдельным `to_attr`; ограничение полей связанных объектов.
- `crmserver/tasks/serializers.py`: чтение подготовленного списка при наличии;
  прежняя SQL-ветка для обычного, неподготовленного объекта сохранена.
- `crmserver/synchronization/test_snapshot.py`: содержимое, права и бюджет SQL
  исходящего снимка на настоящей PostgreSQL.
- `crmserver/tools/scaling_baseline.py`: фаза `--phase sync-read`, использующая
  прежние операции, прогрев, повторения, профили и лимиты; необязательный запуск
  регрессий до HTTP-измерений и fingerprint исходного снимка вне таймера.

Порядок исполнителей задаёт PostgreSQL с прежним `ORDER BY user__username`,
а не Python-сортировка с возможным отличием collation. После prefetch нет
`filter`, `order_by` или `values_list`, обходящих этот список. Неактивные пользователи
по-прежнему присутствуют среди исполнителей, но отсутствуют в активном справочнике.
Удаление membership удаляет M2M-связь; задача без оставшихся назначений становится общей.
Фильтрация `visible_tasks`, nullable UUID, tombstones, даты и порядок записей сохранены.

Новых глобальных maps и копий полного снимка нет. Одиночные JOIN-связи содержат
PK/UUID; Membership/User в prefetch содержат только ключи и username. На каждую
задачу сохраняется список её назначений вместо неиспользуемого prefetch-кэша с
QuerySet и повторных SQL-выборок. Справочник загружает username/first_name/last_name.
Полный `records`, DRF-представления и JSON-тело по-прежнему требуют памяти.
Цена JOIN-prefetch: узкий User создаётся для каждого назначения, тогда как прежний
второй prefetch мог разделять User между несколькими Membership-объектами.
Это O(числа назначений), а не O(задачи × сотрудники). Для видимых admin задач
фикстура даёт 120/600/1 080 назначений. Эту цену сопоставляем с удалёнными QuerySet
на каждую задачу и полными строками клиентов/сделок; точное число байтов Python heap
не измерялось. Рабочий набор процесса приведён отдельно ниже.

## Методика и воспроизведение

Отдельные свежие кластеры PostgreSQL 16.2 / loopback, проектный Python 3.13.2,
Django 6.0.7, DRF 3.17.1, psycopg 3.3.5, Windows. По пять потоков WSGI в одном
Python-процессе, GIL; это не проверка Linux/Gunicorn и не рекомендация workers.
`baseline_settings` использует исключение `.env` из первого этапа до импорта
production settings, искусственные credentials и проверку владельца кластера.
Существующие базы и production не использовались.

Состав/seed=20261016/anchor=2026-10-16 неизменны: 7 организаций, 19 000 живых
записей + 950 tombstones. Целевые org: 400/300/300 + 50, 2 000/1 500/1 500 + 250,
3 600/2 700/2 700 + 450 (клиенты/сделки/задачи + tombstones). Снимки текущего
сотрудника содержат 990/4 950/8 910 элементов. Профилирование и fingerprint —
отдельные, не измеряемые запросы. Сравниваются свежие одинаковые фикстуры.

Диагностика HTTP/sync/SQL включена, sampling=1. Прогрев 2, затем 5 измерений на
каждый из трёх последовательных sync-сценариев. Без правок отправляется полный
ранее полученный снимок; 1% изменений — 10/50/90 клиентов в том же полном пакете;
первичная загрузка — пустой пакет нового устройства. Конкуренция одной org: 1/2/5
клиентов, small по 20 запросов, medium/large по 5. Medium добавляет ограниченную
серию того же сценария, которого не было в исходном baseline. Всего запланировано
135 измерений на версию, плюс прогрев и отдельные профили; UI/диагностический
overhead и разные организации повторно не измерялись.
Параллельные клиенты используют тот же admin-токен своей org, как в baseline:
это несколько клиентов/устройств с одной видимостью, не разные роли пользователей.

Лимиты прежние: HTTP 45 с, SQL statement 25 с, lock 15 с, idle transaction 30 с;
5 потоков, 20 соединений PG, 16 MB ответа, 1 GB артефактов, 1 800 запросов,
watchdog 1 200 с. Таймауты ради результата не увеличивались. Тесты выполняются
до начала замеров в другой БД `test_stage1_disposable` этого же собственного кластера.

PowerShell из корня проекта (каждый каталог вывода должен быть новым):

```powershell
$pg = 'C:/Program Files/ASCON/KOMPAS-3D v23 Study/Libs/PolynomLib/Templates/LocalBase/bin'
$out = Join-Path $env:TEMP 'agrosmena-sync-read-new-run'
& .venv/Scripts/python.exe crmserver/tools/scaling_baseline.py `
  --output $out --postgres-bin $pg --phase sync-read --max-seconds 1200 --verify-tests
```

Для другой установки указать каталог своих PG binaries. Стенд сам создаёт БД,
схему и фикстуры; генератор отказывается работать с заполненной или чужой БД.
`--verify-tests` запускает accounts/web/synchronization/crmserver и unit-тесты
стенда. Серверные sync-интеграции используют временную SQLite headless-служб,
без запуска desktop UI или сборки.

Для ограниченного продолжения используются `--sync-org`, `--sync-scenario`,
`--sync-part`: они выбирают операции, а не сокращают генерацию данных. Во всех
кластерах остаются те же 7 организаций и 19 000 живых записей. Дорогой недостающий
случай выполнялся с `--sync-org large --sync-scenario sync_changed_1pct`; после него
выполняется обычная конкуренция этой org. Отдельная конкуренция small/medium:
`--sync-part concurrency --sync-org small medium`. Её подготовка вне таймера
воспроизводит восемь обновлений тех же клиентов (2 прогрева, 5 изменений, профиль)
через настоящий sync; передаются только изменяемые клиенты. Логическое состояние
перед измеряемыми пустыми pull-пакетами и число записей/версий клиентов сохраняются,
но история чтений/прогрева процесса отличается от монолитного запуска. Внутри
каждой измеряемой серии остаются прежние два прогрева и число повторов.

## Проверки корректности

**88/88 тестов прошли** на PostgreSQL 16.2. Последовательные группы:
accounts/web — 22 теста / 132,099 с; synchronization — 14 / 123,140 с;
crmserver и harness — 52 / 26,520 с. Каждый runner создавал и удалял собственную
`test_stage1_disposable`, основная синтетическая БД измерений не затрагивалась.
Первоначальная попытка единого runner была прервана общим лимитом процесса 180 с
без итогового вердикта suite; она не считается успешной. Тот же лимит сохранён
для каждой последующей группы, HTTP/SQL/lock-timeout не изменены.

Новые пять тестов проверяют полный ответ против обычной сериализации без prepared
атрибута и независимо утверждают поля/UUID/даты, порядок нескольких исполнителей,
включение неактивного и исключение удалённого участника, общие/свои/недоступные и
чужие задачи, все комбинации nullable-связей, удаления клиентов/сделок/задач и
tombstones. Ошибка после успешной входной правки проверяет прежний rollback.

Тест роста **1 → 25 задач** подтверждает настоящий результат с исполнителями и
UUID каждой задачи: один SELECT назначений при обоих размерах и не более шести
SELECT всей подготовки. Полный входящий no-op пакет не меняет этот бюджет.
Наблюдение SQL оборачивает реальную существующую фазу, а не подменяет БД/результат.
Существующие регрессии дополнительно проверяют реальные конкурирующие обмены,
внешнюю atomic-транзакцию, время жизни PostgreSQL-блокировки и откат.

Fingerprint `changes` + `members` исходного снимка **совпал до/после для всех трёх
масштабов**. Он сохраняет порядок списков/записей и все значения, исключает только
динамический `synced_at`. Сверка AST подтвердила неизменность всего тела `exchange`
до блока подготовки ответа и его декораторов. Новых ошибок бизнес-логики в этой
итерации не исправлялось; поведение неактивных/удалённых участников сохранено явно.

## Как интерпретировать время и память

Сокращение SQL подтверждено независимо от времени: подготовка изменилась с
`7 + число видимых задач` до **6 SELECT**, без зависимости от количества задач.
Для измеренных наборов no-op HTTP теперь имеет `2 × размер входящего пакета + 11` SQL вместо
`2 × пакет + задачи + 12`. Для пакета с изменением клиентов добавляются прежние
пять SQL на сохранение каждой изменённой строки. Это не оптимизация входа.

Длительности основных серий неоднородны: малый no-op почти не изменился, средний
и крупный no-op замедлились; крупный пакет с правками ускорился в своём отдельном
повторе. Считать это общим коэффициентом ускорения нельзя. У среднего no-op
неизменённый `apply_ms` вырос с 8 464,5 до 14 084,7 мс, у крупного — примерно вдвое.
Входной код/число проверяемых строк сохранены, а количество SQL уменьшилось только
в ответе. Это поддерживает гипотезу дрейфа среды/стоимости CPU и round-trip, но
не доказывает её: частота CPU, фоновые процессы и точный профиль GC не собирались.
**Наблюдаемый рост HTTP нельзя скрыть или считать исключённой регрессией.** Нужен
контролируемый повтор полного входящего пакета на стабильном стенде.

Из-за этого проведена дополнительная близкая по времени контрольная пара только
первичной загрузки 9 000: настоящий HTTP, одинаковые фикстуры/настройки, 2 прогрева
+ 5 измерений каждой версии, SQL sampling=1, прежние timeout. Старая версия — копия
исходников приложения с двумя сохранёнными файлами до оптимизации, без `.env`,
каталогов БД и media; рабочее дерево не откатывалось. Копия создавалась только из
серверных source/static-каталогов, с отказом при symlink. Новый код запускался из
рабочего дерева. Это ограниченная последовательная пара, не рандомизированный
эксперимент; результаты приведены выше отдельно от основных 135 измерений.

После устранения повторных SELECT остаётся линейный обход полного снимка,
создание ModelSerializer/полей для каждой записи, построение dict и JSON. Код это
подтверждает; отдельные доли CPU этих действий пока не профилировались. При
изменённых задачах входной код дополнительно читает UUID родителей, исполнителей
и права; текущая серия изменяет только notes клиентов и не измеряет такую запись.

HTTP-клиент измеряет время от открытия запроса до чтения тела, без предварительного
JSON-кодирования исходящего пакета. `server_ms` заканчивается готовностью ответа
в middleware; передача по сокету может продолжаться. `response_prepare_ms` включает
все чтения/ORM/сериализацию снимка, но не последующий renderer JSON. SQL duration —
сумма вызовов execute с driver/round-trip/ожиданием блокировки, не чистое время CPU
PostgreSQL. `organization_lock_acquire_ms` также включает SQL/ORM round-trip;
observed hold — наблюдение до выхода сервиса, включая commit при отсутствии внешней
atomic. Медианы отдельных фаз нельзя складывать в медиану HTTP.
Успешный acquire иногда превышает 15 с: PostgreSQL `lock_timeout` ограничивает
ожидание конкретной DB-блокировки, а наш таймер включает также выполнение/driver
и получение процессорного времени Python после ответа БД. Поэтому такой результат
сам по себе не означает неработающий timeout; два отказа подтверждены именно логом PG.

RSS и peak — Windows working set только WSGI-процесса, без PostgreSQL. Peak
накопительный за жизнь процесса, включая прогрев/предыдущие случаи; это не heap
конкретного запроса. В основных возобновлённых сериях история процесса различается,
поэтому их peak не даёт точной оценки экономии на операцию. Контрольная пара имеет
одинаковую историю одного сценария и полезнее для такого сопоставления. В raw JSON
также доступны CPU/RSS клиентского harness. Дополнительной неограниченной структуры
данных оптимизация не создаёт; уменьшение полей и отказ от per-task QuerySet-кэшей
сопоставляются с ценой узких User на назначения, а не объявляются бесплатными.
