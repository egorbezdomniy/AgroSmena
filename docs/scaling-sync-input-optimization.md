# AgroSmena CRM: входные конфликтные чтения sync

Проверки 22–23 октября 2026 года. **Результат частичный: входная оптимизация
не реализована.** В близких парах повторилось ухудшение large; его причина
не установлена. По условию задания переход к изменению бизнес-кода остановлен.
Исходные `scaling-baseline.md`, `scaling-stage-1.md` и отчёт оптимизации чтения
сохранены без переписывания измерений. Hashes подтверждают неизменность приложения.

## Изоляция и метод A/B

`tools/sync_read_ab.py` использует существующий `scaling_baseline.Experiment`:
свежий собственный initdb-кластер, отдельный порт loopback, искусственные credentials,
`baseline_settings` → `verification_settings` с отключением dotenv до импорта settings.
Существующие базы и действующий `.env` не читаются. Старый временный каталог,
удаление которого ранее было запрещено, не используется и не удаляется.

A — сохранённая source-копия до оптимизации исходящего чтения; B — рабочая версия
после неё. Сверка всех 106 Python-файлов сохранённой копии обнаружила отличия
только в `synchronization/services.py` и `tasks/serializers.py`.
Смена source-копии задаёт одновременно cwd, путь server script и PYTHONPATH;
версии не переключаются через reset рабочего дерева. Hashes записаны в `variants.json`.

Один общий синтетический набор seed=20261016, anchor=2026-10-16: семь организаций,
19 000 живых записей и 950 tombstones. Измеряются medium (5 000 живых + 250 удалений,
4 950 элементов входящего снимка) и large (9 000 + 450, 8 910 элементов снимка).
Обеим версиям передаётся один и тот же полный неизменённый пакет. Время `synced_at`
исключено из fingerprints; записи и справочник сотрудников включены.

22 октября планировались четыре блока A/B, B/A, A/B, B/A. После 28 измерений
работа остановлена пользователем: завершены три блока и только B четвёртого.
23 октября выполнена отдельная новая серия AB/BA: 16 измерений, 0 ошибок.
Каждая сторона каждого блока запускается в свежем HTTP-процессе; сначала medium,
затем large, для каждого два прогрева и два измерения. p95 при этой выборке
не рассчитывается. SQL-диагностика включена для всех запросов. Сохраняются обычные
лимиты: HTTP 45 с, PostgreSQL statement 25 с / lock 15 с / idle-in-transaction 30 с,
пять потоков WSGI, до 1 GB артефактов. Watchdog: 1 800 с в прерванной серии,
1 200 с в новой A/B (фактически 1 113,5 с), 900 с в CPU-диагностике (302,0 с).
Это Windows/loopback и один Python-процесс с GIL, не Linux/Gunicorn.

HTTP-клиент измеряет отправку и получение тела; `apply_ms` и `response_prepare_ms`
приходят из серверных событий. SQL duration включает работу драйвера и ожидания,
а не только CPU PostgreSQL. CPU берётся по дельте счётчика процесса в измеренном
блоке; working set после блока и lifetime peak процесса включают прогрев.
Процессы обеих сторон имеют одинаковый порядок запросов, но разные PID.

## Проверенные пути записи и ограничения будущего batching

Текущий вход для каждой записи читает живую модель с `select_for_update` по UUID
и tombstone по entity/UUID, проверяет организацию и max(updated_at), при равенстве
оставляет серверное состояние. Для более новой задачи выполняется отдельная
проверка видимости. Изменённые записи затем проходят прежние проверки связей,
serializer, model save, сигналы, корректировку дат и удаление старого tombstone.

`OrganizationOwnedModel.save()` берёт org lock до сохранения CRM-строки.
Сайт, REST и обычное сохранение из admin используют этот метод. Для удаления
`record_deletion` берёт org lock в pre_delete. Проверен установленный Django
`Collector.delete`: pre_delete вызывается до fast deletes, SET_NULL и DELETE.
Каскады клиента удаляют сделки, создают tombstones и меняют ссылки/даты задач.
Поэтому сохранённое до каскада состояние дочерних строк использовать нельзя.

Назначения задач сохраняются также через M2M после выхода из model save.
Управление membership через accounts services берёт org lock, но обычный admin
Membership не использует эти сервисы. Поэтому org lock не доказывает неизменность
назначений/справочника. Проверки доступности и связей не следует заменять
предварительно прочитанными maps. Произвольные ORM/SQL-записи за пределами
проверенных путей не покрываются гарантиями приложения.

HTTP `ExchangeSerializer` уже запрещает повтор одного (entity, UUID) во всём пакете.
Сортировка service сначала обрабатывает удаления, затем живые записи с порядком
customers → deals → tasks. Это существующая семантика; входной порядок не является
хронологией операций create/update/delete. Ослаблять запрет дубликатов или менять
сортировку в этой оптимизации нельзя.

Пакетный FOR UPDATE меняет момент и порядок захвата строк. Совместно с org lock
нужно отдельно проверить, что batching не начинает блокировать строки чужих
организаций заранее, и сохранить актуальные проверки при отсутствующей записи.

## Дополнительная CPU/GC-диагностика

Четыре свежих процесса **A B B A**, только large, одинаковый полный no-op пакет,
два прогрева и одно измерение в каждом. Medium перед large здесь отсутствует;
это отдельная диагностическая серия, её latency не смешивается с основной A/B.
4 измерения, 0 ошибок; с прогревом 12 запросов плюс отдельная подготовка пакета.
Здесь ухудшение B не воспроизвелось.

Обе сохранённые source-копии прочитаны в новые собственные каталоги. В обеих
изменён только экспериментальный `baseline_server.py`: установлен одинаковый
локальный probe, который оборачивает настоящий `sync_phase`, считает thread CPU,
thread cycles и GC callbacks. Бизнес-файлы не изменены. Перед фазой, вне её
нативного таймера, выполняются одинаковые 100 000 целочисленных итераций.
Checksum всех reference-проб равен 150077. Эти вмешательства могут влиять на
исполнение, поэтому серия диагностическая, а не новый baseline.

## Что изменено и проверено

- `tools/sync_read_ab.py`: сохранение client-результатов прогрева в отдельный
  JSONL и отказ продолжать блок после неуспешного прогрева. Исправление внесено
  после выполненных серий; ретроспективно недостающие client-статусы не восстановлены.
- `tools/analyze_sync_input.py`: offline-анализ сопоставимых пар, явное исключение
  проблемного прогрева, ошибки отдельно, p95 только при >=20 успешных наблюдениях.
  Проверен на фактических артефактах, включая ожидаемое исключение блока 0 large.
- `tools/sync_cpu_diagnosis.py`, `tools/sync_cpu_probe.py`: ограниченный ABBA на
  собственном PostgreSQL и копиях источников, измерение CPU/GC только в диагностике.
- Этот отчёт. Синтаксис четырёх tools проверен; три существующих unit-теста
  baseline harness прошли. Они не подменяют настоящие HTTP/PostgreSQL-измерения.

`synchronization/services.py`, `tasks/serializers.py`, модели, сигналы, настройки,
протокол и транзакции в этой итерации не менялись. Подготовленные черновики
тестов/запускателя будущей входной оптимизации не включены в итоговый diff.
88 тестов предыдущей итерации не запускались повторно и не считаются новыми
успешными проверками. Новый бюджет входных SELECT и бюджет снимка <=6 отдельно
не проверялись: входная реализация осталась прежней.

## Отложенная часть и следующий шаг

Пакетные чтения, новые maps и гарантии их последовательной корректности **ещё
не реализованы и не проверены**. Не выполнялось сравнение текущей и новой входной
реализации на 1 000/5 000/9 000: новой реализации нет. Сценарии 1% изменений,
пустого пакета, конкурентной записи через сайт/REST/sync, rollback и проверки
роста SELECT этой итерации отложены до прохождения диагностического условия.

Кандидат после выяснения причины: порции до 500 UUID одной entity, узкие метаданные
собственных строк с сохранением FOR UPDATE, batch tombstones с сохранением проверки
чужих UUID, сброс maps после любой применяемой операции. Полные объекты нужны лишь
перед изменением; связи и видимость задач читаются актуально. Отсутствующие/чужие
строки могут потребовать прежних отдельных чтений. Это проект, не гарантия:
нужны тесты дубликатов, старых/равных/новых дат, живой записи вместе с tombstone,
каскадов, очищения ссылок, rollback и реального пересечения с сайт/REST/sync.
Ранний захват batch row locks требует отдельной оценки deadlock, особенно при
чужих UUID; org lock сам по себе не покрывает M2M и все admin-пути.

Следующий диагностический шаг — захватить CPU-профиль именно ухудшившегося apply
в близком A/B вместе с состоянием CPU/планировщика; проверить влияние размещения
потока и режима питания в отдельно обозначенной контрольной серии. Не приписывать
причину окружению по совпадающему AST и не увеличивать timeout для получения успеха.
