`O` ниже — `Organization FOR UPDATE`. `T` — запись Task. Таблица описывает
**состояние после исправлений** при неизменной организации редактируемой задачи.
У SQL INSERT/UPDATE/DELETE и FK есть также собственные неявные блокировки;
org lock не превращает READ COMMITTED в единый снимок всех связанных таблиц.

| Путь записи | Транзакция и порядок блокировок | Что может видеть sync | Фиксация для текущего sync |
| --- | --- | --- | --- |
| Сайт: создание/редактирование Task | Теперь `TaskEditor.form_valid` atomic: O из `Task.save` → INSERT/UPDATE T → `form.save_m2m` → commit. Валидация формы раньше | Ждёт O; окно «новая строка/старые назначения» закрыто | `Task.updated_at` от save и M2M фиксируются вместе |
| REST: POST/PUT/PATCH Task | Теперь `perform_create/update` atomic: O → T → `assignees.set` → commit. `is_valid` раньше | То же; ошибка M2M откатывает строку и связи | Дата от model save; отдельного события назначения нет |
| Sync: входная задача | Уже был общий `exchange.atomic`: O → повторная проверка допуска → FOR UPDATE T → save с повторным O → M2M → даты из пакета → снимок → commit | Другие sync и обычные Task writers ждут O | Клиентская дата и назначения одной операции атомарны; формат сохранён |
| Django admin: Task | Стандартный POST `changeform_view` atomic: `save_model` берёт O → T → `save_related` пишет M2M → commit | При стабильной организации задачи окно не воспроизводится; тест подтверждён | Дата от save; M2M вместе с ней |
| Регистрация организации | `register_organization.atomic`: INSERT новой Org → User → Membership; отдельного O нет | До commit ещё нет доступной пользователю пары Org/Membership | После commit новый полный справочник |
| Сайт: добавить пользователя / поменять роль | `add_user/change_membership.atomic`: O → проверка администратора → User+Membership INSERT либо Membership UPDATE | Эти операции сериализованы O | Membership имеет свою дату; роли в sync-справочнике не передаются |
| Сайт: удалить участника | `change_membership.atomic`: O → проверка последнего admin → Collector, повторный O → DELETE M2M → DELETE Membership | До либо после удаления; аккаунт User сохраняется | Назначения удаляются; пустой набор делает задачу общей. Дата Task не повышается |
| Admin: создать Membership | POST atomic, INSERT Membership, FK-проверка Org при commit; явного O нет | На PG подтверждено: commit ждёт O, строка до этого не видна | Новый участник попадёт в следующий полный справочник |
| Admin: изменить Membership (роль/user/organization) | POST atomic, UPDATE Membership, без явного O. Изменённые FK имеют свои проверки | Роль доказанно коммитится при удерживаемом O. Для переноса org нельзя считать защищёнными обе организации | Меняется дата Membership; Task и его дата автоматически не меняются; роль не передаётся, username берётся через User |
| Admin: удалить Membership; удалить User с каскадом; delete_selected | Collector atomic, плюс outer atomic одиночного admin delete. Теперь pre_delete Membership берёт O до удаления through-строк. Для queryset выбирает затронутые Org по PK ↑ → M2M DELETE → Membership DELETE → при каскаде User DELETE | Удаление ждёт завершения снимка. Одиночные и массовые пути проверены | Member исчезает из справочника и назначений. Member-delete сохраняет User; User-delete удаляет аккаунт, как и раньше |
| User: is_active false/true в admin | Стандартный admin POST atomic, UPDATE User; O нет. Отдельного поля активности Membership **нет** | Флаг может меняться при удерживаемом O. Sync теперь повторно проверяет его после ожидания O; уже допущенная операция не отменяется автоматически | Новая аутентификация видит актуальный флаг. Неактивные исключены из справочника, но остаются в существующих назначениях |
| User: создание/профиль/имя/username | Формы регистрации/add_user входят в свои atomic; обычный ProfileForm.save — save User без O; admin User — outer atomic без O | Поля User не защищены O. Профиль не предоставляет изменение активности или username; admin предоставляет | Имя/логин отражаются следующими SQL чтениями. User без Membership сам по себе не получает CRM-доступ |

Область таблицы: текущие views/forms/serializers/services и стандартные admin handlers.
Прямой `Task.assignees.add/remove/clear/set` имеет транзакции менеджера M2M,
но не общий org lock и не повышает дату Task. Прямой `Membership.save` также
не имеет общего org lock. В текущих HTTP-путях Task внешняя транзакция теперь
покрывает manager calls; это не универсальная гарантия для shell, raw through
записей или будущего кода, обходящего эти пути.

## Подтверждённые дефекты и точечные изменения

1. **Промежуточная запись Task на сайте/REST.** Поток остановлен непосредственно
   перед настоящим `assignees.set`, после возврата `Task.save`. До исправления
   sync на другой DB-сессии успевал закончиться: metadata уже были закоммичены,
   назначений новой приватной задачи ещё не было. Это окно позволяло представить
   её как общую. Исправлено внешними atomic только в `TaskEditor.form_valid`
   и `TaskViewSet.perform_create/perform_update`.
2. **Удаление в admin обходило org lock.** DELETE Membership и каскад User
   коммитились, пока sync был остановлен между сериализацией задач и чтением
   справочника. Теперь `synchronization.signals.lock_membership_deletion`
   берёт org locks в Collector.pre_delete до удаления M2M. Для массовых удалений
   порядок Org PK ↑, а не порядок Membership/User PK. Проверен реальный порядок:
   ожидающий на младшей Org delete ещё не держит старшую Org (`NOWAIT` probe).
3. **Устаревший допуск после ожидания O.** Уже аутентифицированный sync продолжался
   с HTTP 200 после завершённой деактивации User. Теперь проверяется в БД та же
   Membership PK + user + organization + `user__is_active=True`. После отзыва и
   повторного создания membership старый ожидающий запрос также получает 403;
   новый запрос с актуальным membership допустим. Inactive на новой аутентификации
   получает 401; реактивация восстанавливает прежний доступ.

Другие изменённые файлы — `accounts/test_assignment_consistency.py` и
`tools/isolated_server_tests.py` (стенд без генерации baseline-данных).
Модели, правила назначения, политика удаления, ограничения последнего admin
в сервисах сайта и протокол не изменены. Внутренняя транзакция exchange сохранена.

## Почему отсутствие новой даты назначения не равно потере данных

Удаление Membership удаляет through-строки и не меняет `Task.updated_at`.
Tombstone Membership в протоколе нет. Это подтверждённое свойство, а не исправленная
здесь ошибка: `app/repositories/sync_repository.py:apply_snapshot` применяет
**полный авторитетный ответ**, включая поля назначений, без пропуска равных дат.
Сервер при равных датах оставляет своё состояние и возвращает актуальные связи.
Тест проверяет: удалён последний исполнитель → аккаунт сохранён → задача общая
и присутствует в полном ответе с пустым `assignee_usernames`.

Деактивация User не удаляет Membership и назначения. Поэтому задача только
с неактивным исполнителем **не становится общей**. Имена неактивных исполнителей
могут остаться в задаче, отсутствуя в активном справочнике; это существующее
поведение, проверенное также прежними SnapshotTests.

## Точные ограничения будущего batching

- При стабильном owner O теперь защищает **полную запись Task и назначений** в
  перечисленных Task writers и удаление Membership. Но Task FOR UPDATE сам
  по себе не блокирует User, Membership и все through-операции.
- **Нельзя заморозить Membership/User/active/username/роль/видимость на весь пакет
  лишь потому, что взят O.** Admin role-update реально прошёл под чужим O;
  активность User также не берёт O. Нужны актуальные проверки либо отдельно
  согласованный общий порядок записи этих данных.
- Глобальный admin позволяет менять organization/user у Membership и owner у Task,
  а выбор исполнителей TaskAdmin не ограничен организацией. Эти maintenance-пути
  не унифицированы этим исправлением. Нельзя предполагать защиту старой и новой
  Org одновременно или универсальный инвариант same-org для M2M. Совместные
  гонки переноса владельцев/смены user здесь не тестировались; эти гарантии не даны.
- Валидация TaskForm/TaskSerializer происходит до внешней транзакции сохранения.
  Результаты её Membership lookup не являются долгоживущим доказательством наличия
  и активности участника после ожидания. Данные ранее применённых операций и каскадов
  тоже должны отражаться в любых будущих maps. Допуск sync после O перепроверяется,
  но нет обещания отмены уже допущенной операции при последующем отзыве доступа.
- Нельзя использовать только `Task.updated_at` как версию M2M/membership/справочника
  и пропускать связанные чтения на этом основании. Текущий полный импорт работает
  иначе; новая версия назначений/дельта-протокол в этом задании не вводились.
- Оценка порядка batch row locks и взаимодействия с глобальным admin всё ещё нужна.
  Новых серий производительности не было. Прежние baseline относятся к коду **до**
  этих исправлений; будущий контроль перед оптимизацией должен учитывать новый diff.

## Завершение аудита целостности

23 октября 2026, отдельная итерация. Производительность и batching не исследовались.
Проверены текущие HTTP writers и установленный Django: admin POST действительно
выполняет валидацию формы, save_model и save_related внутри одной atomic.
Безопасной операции переноса CRM/Member между организациями в коде нет.

### Воспроизведённые дефекты

- Admin POST создания и изменения Task принимал Membership другой организации
  (302), включая смесь своих и чужих исполнителей.
- Admin POST переносил существующие Customer, Deal и Task в другую организацию;
  смена organization или user существующего Membership также принималась.
  Связи и назначения зависимых строк автоматически не переносились.
- После успешной валидации REST/сайта запрос ожидал O. Завершённая за это время
  деактивация выбранного User не мешала сохранению назначения. Удаление выбранного
  Membership в таком окне давало ошибку FK на commit (500 у REST и admin).
- Остановка настоящего assignees.set после Task.save показала, что UPDATE User
  мог завершиться до commit задачи. Повторный SELECT без row lock не закрывает
  вторую половину этого окна.

В исходном наборе из 10 test methods две уже безопасные проверки прошли:
межорганизационные customer/deal в admin отвергались модельным clean;
неактивное назначение в admin сохранялось, явное очищение делало задачу общей.
Остальные проверки дали **13 failed assertions в subtests/методах и 2 errors**.
Ошибки FK и успешные недопустимые POST наблюдались на настоящей PostgreSQL.

### Минимальные исправления и актуальные пути

| Путь | Серверная защита и транзакция | Результат |
| --- | --- | --- |
| Admin: organization существующих Customer/Deal/Task | OrganizationOwnedModel.clean и save сверяют сохранённую organization_id; save сохраняет прежний O | Перенос отвергается ошибкой формы; простое model.save также отвергает его. Нет операции переноса зависимых данных |
| Admin: organization/user существующего Membership | Membership.clean и save запрещают смену сохранённых FK | Ошибка поля; роль менять можно как раньше. Создание и удаление Membership не заменены переносом |
| Admin: назначения Task | TaskAdminForm.clean внутри admin atomic: O → свежие выбранные Membership своей Org с row locks User по PK ↑ → проверки → Task.save → M2M → commit | Чужие/удалённые Membership отвергаются формой. Проверка действует на POST независимо от вариантов UI. Неактивные свои исполнители допустимы как прежде |
| Сайт: назначения Task | В прежней TaskEditor.form_valid.atomic: O → выбранные User по PK ↑ → повторная проверка наличия/активности → Task + M2M → commit | Устаревший выбор возвращает ошибку поля без изменения строки/назначений |

REST получает 400 при устаревшем выборе; sync откатывает весь обмен |

Реализация — `tasks.models.lock_task_assignees`. После O она читает **только
выбранные PK своей организации**, присоединяет User и берёт
`FOR NO KEY UPDATE OF auth_user` с `ORDER BY user_id`. Проверки используют результат
после ожидания блокировки, а не кэш формы/serializer. Lock удерживается внешней
транзакцией до commit/rollback, включая запись M2M. Набор чужой организации не
приводит к блокировке её User. Нулевой набор остаётся общей задачей.

O нужен для сериализации с Task writers и удалением Membership через Collector.
Неизменность Membership.user/organization обеспечена clean/save, а не только UI.
Блокировка User нужна отдельно: is_active/username в admin не берут O. NO KEY
UPDATE конфликтует с изменением этих полей и удалением User, сохраняя совместимость
с обычной FK KEY SHARE проверкой. Membership row locks дополнительно не введены.
В sync существующий Task FOR UPDATE по-прежнему берётся после O, до serializer;
в остальных путях Task пишется после User locks. Для одной Org первый O
сериализует эти порядки. Между Org выбранные User не пересекаются: Membership
имеет OneToOne User, смена его идентичности запрещена обычным save.

Текущие User admin edits не запрашивают O после UPDATE User. Удаление User/Member
берёт O до удаления через прежний pre_delete. Массовое admin-удаление сохраняет
порядок Org PK ↑. Нового подтверждённого deadlock в этих путях не получено;
гарантия для произвольных будущих транзакций с порядком User → O не даётся.

Изменённые файлы этой итерации:

- `crmserver/models.py`: общая проверка неизменных FK, защита владельца CRM;
- `accounts/models.py`: неизменность user/organization Membership;
- `tasks/models.py`: helper блокировки и проверки выбранных исполнителей;
- `tasks/admin.py`: серверная проверка admin-формы внутри её atomic;
- `tasks/serializers.py`, `web/views.py`: защищённая проверка перед сохранением;
- `accounts/test_organization_integrity.py` и этот отчёт.

### Точные оставшиеся исключения

- Это защита перечисленных HTTP writers и обычного model.save от смены identity,
  **не ограничения уровня БД**. Прямые QuerySet.update/bulk/raw SQL обходят clean/save;
  прямые Task.assignees manager/through-записи обходят helper. У прямого ORM создания
  CRM со связями customer/deal save по-прежнему не вызывает полный clean автоматически.
  Для нового writer эти проверки и внешняя atomic обязательны. Массовой очистки
  ранее существовавших некорректных данных не выполнялось: реальные БД не читались.
- Активность проверяется для явного нового выбора на сайте/REST/sync. PATCH без
  assignee_usernames не перепроверяет и не очищает существующие назначения.
  Admin по-прежнему допускает своего неактивного исполнителя. Деактивация после
  commit не удаляет назначения и не делает задачу общей. Удаление последнего
  Membership делает задачу общей и сохраняет User по прежним правилам сайта.
- User locks защищают выбранных исполнителей до конца транзакции, **не весь
  справочник пользователей**. Роли, другие User и активность уже допущенного
  sync-актора не заморожены одним O. Полный снимок справочника не получает новой
  гарантии единого момента времени. Дата Task при удалении Membership не повышается.
- Helper требует внешней atomic (она есть у всех указанных вызовов); самостоятельный
  вызов serializer/admin-формы вне этих handlers не является новым поддержанным
  транзакционным API. Порядок User PK ↑ действует для одного выбора, не для
  произвольного будущего пакета блокировок. Оснований для кеширования видимости,
  активности или directory на весь sync-пакет и для batching этим аудитом не дано.
