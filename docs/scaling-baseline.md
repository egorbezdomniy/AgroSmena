# AgroSmena CRM: синтетический baseline до оптимизаций

Дата набора: 16 октября 2026. Это локальный воспроизводимый эксперимент на искусственных
данных, а не оценка числа поддерживаемых пользователей и не проверка Linux/Gunicorn.
Бизнес-код, права, sync-протокол, индексы и границы транзакций не оптимизировались.
Изменения первого этапа сохранены; добавлены только файлы экспериментального стенда
и этот отчёт. Исходники, handoff и `docs/scaling-stage-1.md` сверены перед запуском.

## Среда и изоляция

Используется тот же проектный Python 3.13.2 / Windows, Django 6.0.7, DRF 3.17.1,
psycopg 3.3.5, WhiteNoise 6.12.0 и PostgreSQL 16.2. Точные версии ОС, число логических
CPU и hashes исходников записаны в `environment.json` каждого прогона.

`crmserver.baseline_settings` использует подготовленный на первом этапе
`verification_settings`: DJANGO_LOAD_DOTENV=false **до импорта настроек**, DEBUG=false,
искусственный ключ и пользователи, PostgreSQL host строго 127.0.0.1. Ни действующий
`.env`, ни пользовательские базы/данные не использовались. Унаследованные PG-параметры
удаляются, maintenance connection получает искусственный password и несуществующий
passfile внутри каталога эксперимента.

Каждый запуск требует **новый, ещё не существующий** каталог. В нём создаются marker
владения, новый initdb-кластер, свободный порт и база `baseline_synthetic`. Перед
генерацией проверяются settings module, marker/port, `SHOW data_directory` и имя БД.
Наличие записей вызывает отказ; API очистки или truncate произвольной базы нет.
Фикстуры создаются ORM bulk-операциями вне измерений с согласованными FK/M2M;
это ускорение подготовки тестовых данных, а не изменение production CRUD/sync.
После загрузки выполнен ANALYZE, но новые индексы не добавлялись.

PostgreSQL: shared_buffers=64MB, max_connections=20, max_wal_size=128MB,
fsync/synchronous_commit не отключались. CONN_MAX_AGE=0 сохранён: измерения включают
обычную цену новых соединений. SQL statement timeout=25 с, lock timeout=15 с,
idle-in-transaction timeout=30 с действуют только на экспериментальные подключения.
HTTP timeout=45 с, тело ответа ограничено 16 MB. Максимум 5 HTTP-клиентов/потоков,
1 800 запросов, 1 GB артефактов и общий watchdog 1 200 с; процессы останавливаются в
finally. При аварийном watchdog разрешён immediate stop **только собственного** кластера.

HTTP — настоящий loopback WSGI через wsgiref с ограниченным ThreadPoolExecutor(5).
Это даёт реальную конкуренцию запросов и PostgreSQL-соединений, а не очередь одного
последовательного worker. Это один Python-процесс с GIL, без TLS/proxy/production
балансировщика и без браузерного рендеринга; результаты не переносятся на Gunicorn.
Дополнительные потоки не являются рекомендацией production: процессный throttle
из первого этапа остаётся ограничением. Login и генерация сессий/токенов выполняются
до замеров; используются реальные Django sessions и sync Bearer auth. Тестовый
HTTP-клиент явно передаёт искусственную session cookie на loopback; это не проверка HTTPS.

## Методика

- Для страниц: 2 прогрева, затем 20 успешных/ошибочных попыток каждого сценария.
  Счётчики ошибок включают каждый non-200/timeout; latency рассчитывается по успешным
  ответам, ошибки не превращаются в нулевую длительность.
- Для дорогих последовательных sync: 2 прогрева и 5 измерений. Медиана, min/max и
  сырые точки доступны; p95 не публикуется. 20 повторов здесь неоправданно расходовали
  бы общий ограниченный бюджет и не позволили бы выполнить остальные сценарии.
- Sync unchanged отправляет полный ранее полученный снимок без новых временных меток.
  Sync changed обновляет notes и timestamp у 1% всех живых записей — 10/50/90 клиентов,
  но по прежнему протоколу передаёт весь снимок. Каждое повторение действительно
  обновляет эти записи. Первый обмен пустого нового устройства передаёт `changes=[]`
  и получает полный разрешённый снимок; это не импорт 9 000 новых локальных записей.
- Конкуренция small: 1, 2, 5 клиентов; по 20 запросов. Пять равных small-организаций
  позволяют сравнить same/different org без смешения размеров. Смешанная серия
  чередует dashboard и sync pull; в отчёте маршруты разделены (по 10 наблюдений).
  Для large — по 5 sync pull на каждый уровень конкуренции; без p95.
- Диагностика: отдельные серверные процессы с одинаковыми данными. Off оставляет
  middleware/request ID, но выключает события/SQL. Http включает HTTP/sync без SQL.
  Sql включает SQL для 100% запросов. Три блока с порядком off→http→sql,
  sql→off→http, http→sql→off; в каждом 3 прогрева и 20 повторов dashboard и sync pull.
  Итого 60 точек на режим/операцию. Оценивать также медианы отдельных блоков;
  небольшую разницу внутри вариативности нельзя объявлять низким overhead.
- p95 — ближайший сверху порядковый статистический элемент ceil(0.95*n), только
  при n>=20 успешных наблюдений. Для n=20 он особенно неустойчив. p99 нигде не считается.
  Кэши ОС/PostgreSQL не сбрасывались: это прогретый baseline, не cold-start benchmark.
- HTTP client clock — perf_counter от создания opener/open до полного read тела;
  JSON encoding запроса и parsing ответа находятся вне этого времени. App duration
  — штатная метрика middleware до response ready, без передачи тела. Отдельная WSGI
  ready-метрика стенда симметрично доступна и при выключенной диагностике.
- Стенд фиксирует время очереди собственного executor от accept до начала worker.
  Это не очередь PostgreSQL. Organization lock acquire включает SQL/ORM round-trip,
  поэтому не называется чистым DB wait. Низкая очередь HTTP вместе с acquire и
  сравнением same/different org помогает отделить эффекты; дополнительных workers
  production из этого не выводим.
- CPU и working set Windows измеряются для **созданного HTTP-процесса**, отдельно от
  controller/client. CPU ms/req — разница process CPU между границами серии / число
  запросов, не время одного SQL. RSS — наблюдение после серии; lifetime peak — максимум
  процесса с его старта, не peak конкретного endpoint. CPU PostgreSQL/всего хостинга
  не восстановлен из HTTP-времени. Эти поля вместе с client CPU/RSS сохранены в JSON.
- SQL profiles выполняются отдельными помеченными запросами после серий и не входят
  в таблицу latency. SQL/параметры не добавлялись в production logger: локальный
  wrapper внутри синтетического сервера агрегирует шаблоны и сохраняет только здесь
  SQL, counts, time и стеки. Группировка ограничена 150 шаблонами (у changed sync
  уникальные SAVEPOINT имена могут упереться в предел); полные SQL-счётчики основной
  диагностики от этого ограничения не зависят.
- EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON) выполнен только для выбранных SELECT из
  этих профилей, без FOR UPDATE, внутри READ ONLY transaction с timeout=5 с.
  Statements записи не исполняются для анализа планов. Планы показывают локальную
  цену выбранного запроса, а не распределение HTTP latency.

## Воспроизведение и артефакты

Из каталога `crmserver`, проектным Python, указать путь только к **бинарным файлам**
PostgreSQL и новый каталог артефактов (в примере переменные PowerShell):

```powershell
$baselineOutput = 'C:\temporary\agrosmena-baseline-NEW'
$baselinePgBin = 'C:\path\to\PostgreSQL\bin'
..\.venv\Scripts\python.exe tools/scaling_baseline.py --output $baselineOutput --postgres-bin $baselinePgBin --max-seconds 1200 --anchor-date 2026-10-16
..\.venv\Scripts\python.exe tools/analyze_scaling_baseline.py --root $baselineOutput
```

Не указывать существующую базу/порт: основной runner сам создаёт кластер и выбирает
порт. Не использовать `tools/local_postgres.py`: он предназначен для разработки и
читает действующий `.env`. Артефакты: `dataset.json`, `environment.json`, `samples.jsonl`,
`results.json`, `events-*.jsonl`, `profile-index.jsonl`, `profiles/*.json`,
`analysis.json`, `result-tables.md`, `cleanup.json`. Session/Bearer tokens не записываются
в эти файлы; SQL/планы содержат только искусственные значения.

Для наблюдения PostgreSQL в отдельном терминале можно выполнить:

```powershell
..\.venv\Scripts\python.exe tools/baseline_observe.py --root $baselineOutput --after-catalog --max-seconds 700
```

Наблюдатель ждёт завершения последовательных серий и затем раз в 100 мс читает
только агрегаты `pg_stat_activity` собственного кластера: число active/Lock/соединений.
Он не выбирает query text, пользователей и содержимое таблиц. Дополнительное
подключение входит в лимит 20. Это дискретные наблюдения наличия ожидания, не точное
lock_wait_ms отдельного запроса. Периодически сохраняются размер БД и wal_bytes
нового кластера; wal_bytes — генерация, не объём WAL на диске.

Если общий бюджет исчерпан, оставшуюся фазу можно выполнить **после остановки первого
прогона**, на новом таком же наборе, отдельным ограниченным запуском:
`--phase overhead --max-seconds 600` либо `--phase concurrency --max-seconds 600`.
Не запускать фазы параллельно: иначе они будут влиять на CPU/кэши друг друга.
Сравнение overhead проводить внутри одной фазы с одинаковыми данными для всех режимов,
а не вычитать latency из разных запусков.

слепого добавления индексов. Для каталога исследован малый набор: выводы о большом
каталоге и хранении фотографий из него делать нельзя.

### Что дали планы

Отдельные планы горячих lookup tombstone и запросов исполнителей используют
индексные обращения/небольшие joins и сортировки; в профилях unchanged выбранные
SELECT занимали около 0.03–0.13 мс внутри EXPLAIN на этом PostgreSQL. Это не 0.13 мс
end-to-end и не среднее по всем SQL: EXPLAIN не учитывает каждую клиентскую поездку
и Python/DRF. Умножение числа коротких запросов, разбор полного пакета и сериализация
объясняют существенно больше времени, чем один дорогой план. Точные JSON-планы,
буферы/rows/index names и источник каждого SQL находятся в `profiles/*.json`.

### Гипотезы и ограничения причинного вывода

- Потери на GIL/конкуренцию CPU могут объяснять ухудшение different-org при пяти
  клиентах без заметного DB lock wait. Это гипотеза для сравнения с Linux/multiprocess;
  одни duration и process CPU не доказывают точную долю GIL.
- Нет замеров реальной сети, TLS, reverse proxy, browser DOM, диска/CPU production
  PostgreSQL или холодного старта. Работа SQL через loopback Windows и локальный
  fsync имеет собственную цену. Нельзя обещать число поддерживаемых пользователей.
- RSS после крупных ответов не доказывает утечку памяти: Python allocator и lifetime
  peak отличаются от живого объёма одной операции. Длительное исследование памяти
  здесь не выполнялось.
- Sync по-прежнему полный. Пустой пакет нового устройства и полный пакет без
  изменений выполняют разную работу; их нельзя смешивать в общую метрику sync.

## Интерпретация диагностики и конкуренции

На dashboard SQL-режим был медленнее off в парных блоках на 2.4%, 4.6%, 6.5%.
Это наблюдение данного стенда, а не доказанная универсальная стоимость SQL wrapper.
Всего три блока, вариативность отдельных запросов велика; точный маленький эффект
без доверительных интервалов и повторения в целевой среде не установлен.

Для sync SQL/off меняется от −2.5% до +2.0% по блокам; HTTP/sync-only даже выглядит
быстрее off (−7.8%…−0.8%). Это не «ускорение от логов», а свидетельство дрейфа/шума
среды. Нельзя заявить пренебрежимо малый overhead или обещать конкретный процент.
Полное сравнение использует только отдельный завершённый прогон, без смешения с
оборванной первой попыткой и без параллельного запуска другой фазы.

Small same-org c=5: acquire median 1 546.8 мс, до четырёх DB waiters, executor queue
median 0.2 мс / max 3.4 мс. Different-org c=5: acquire median 3.4 мс, DB waiters=0.
Таким образом ожидание org lock подтверждено независимо от очереди executor.
При этом different-org HTTP median 3.60 с хуже same-org 2.62 с: отсутствие row-lock
не означает отсутствие CPU/GIL/DB contention в одном процессе. Ограничение Windows
single-process стенда здесь существенно; вывод о production workers не делается.

Dashboard одновременно с sync: medians HTTP 176/449/465 мс при 1/2/5 клиентах.
Сам dashboard не берёт этот SELECT FOR UPDATE: ухудшение нельзя назвать ожиданием
org lock у dashboard. Чистый lock wait по длительности acquire не вычислялся.
Executor queue считается **после accept**; kernel/listen backlog и очередь до accept
не измерены. Разность client и app duration включает также TCP, parse/read тела,
планирование и передачу ответа, а не одну «сетевую задержку».

## Результат запуска, ошибки и незавершённые сценарии

- Windows 11 build 26200, 18 логических CPU. Наблюдённый lifetime peak HTTP-процесса
  основного прогона — 163.2 MiB, controller/client — 120.6 MiB. Это разные процессы;
  их CPU/RSS не объединяются с PostgreSQL. Остальные CPU/RSS точки — в таблицах и JSON.
- Основной прогон: 48 последовательных сценариев/масштабов — 825 измерений, 0 ошибок;
  12 серий конкуренции — 195 измерений, **1 ошибка**. Итого для основных таблиц
  1 020 наблюдений, 1 ошибка. Нет отсутствующих SQL/app correlations в успешных
  SQL-измерениях; проверенные hashes измеряемого исходного кода не изменились.
- Большая org, c=5: 4 успеха и 1 HTTP500 с outcome=database_error. PostgreSQL журнал
  подтверждает `canceling statement due to lock timeout`; acquire ошибочного вызова
  15 022.6 мс. Это установленный **только стендом** lock_timeout=15s, а не значение
  production. Ошибка включена в счётчик; latency/фазы успешных запросов не смешаны
  с ней. p95 при четырёх успехах отсутствует.
- Основной процесс завершился по предусмотренному общему лимиту через 1 200.7 с,
  exit 1 / TimeoutError. Все основные сценарии и конкуренция к этому моменту
  завершились; оборвалась overhead-фаза. Три завершённых частичных серии (60 точек)
  сохранены в её raw JSON, но исключены из итогового сравнения диагностики. Точки
  незавершённой следующей серии не были checkpointed как полная серия и не выданы
  за завершённые клиентские измерения; server events сохранены для аудита.
- Сравнение диагностики повторено отдельно, **на свежем наборе того же состава**,
  без обновлений предыдущей фазы: 360 измерений, 0 ошибок, 444.0 с, exit 0,
  unfinished=[]; 60 точек на каждый режим/операцию. Все режимы внутри этого прогона
  работают с одинаковыми данными. Итого в опубликованных таблицах **1 380 измерений**.
- Дополнительно: 21 отдельный успешный profiling request, 83 успешных SELECT-плана
  EXPLAIN ANALYZE; они не входят в latency-выборки. DB observer дал 3 846 наблюдений,
  максимум четыре Lock waiters. На последнем resource sample: БД 28 537 315 bytes,
  кластер сгенерировал 71 810 867 bytes WAL. Это не размер WAL на диске и не CPU БД.
- Два ранних пробных запуска стенда исключены. Первый остановился до измерений
  из-за sys.path при импорте Django project; путь исправлен. Во втором повторный
  django.setup() перенастроил logging destination, а план из 20 дорогих sync-повторов
  оказался чрезмерным. Sink перенесён после последнего setup, sync-повторы ограничены
  пятью. Его предварительные числа не смешивались с финальными.
- Три unit-теста самого harness прошли: отказ существующему output до запуска
  процессов, p95/error accounting, сохранение return/exception при лимите SQL profile.
  Проверка синтаксиса новых модулей и git diff --check прошли. Это дополняет, но
  не заменяет настоящие HTTP/PG измерения. Первый вариант temporary-directory unit
  упёрся в ACL Windows sandbox при cleanup; тест использует существующий tools dir
  для проверки отказа без создания временных каталогов и успешно повторён.

Все запрошенные категории измерены. Не выполнялись начальный импорт 9 000 новых
локальных записей, холодный старт, browser UI, real TLS/proxy, Linux/Gunicorn,
performance на реальных данных и длительный memory/нагрузочный soak: они не входят
в опубликованный baseline. Пять sync-наблюдений недостаточны для достоверного p95;
этот пробел обозначен прочерком, а не скрытым расчётом p99.
