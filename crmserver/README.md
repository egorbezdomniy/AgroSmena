# CRM v0.5 — пользователи, организации, веб-интерфейс и API

Django 6 + Django REST Framework + PostgreSQL. Desktop-приложение не изменено;
Добавлена ручная синхронизация с desktop; мобильного приложения нет. Веб-интерфейс реализован на
Django Forms и Templates без frontend-фреймворков и внешних CDN.

## Запуск

Из корня репозитория (Python 3.12+):

```powershell
.\.venv\Scripts\python.exe -m pip install -r crmserver\requirements.txt
cd crmserver
Copy-Item .env.example .env
# Заполните .env параметрами отдельной существующей базы PostgreSQL 14+.
# DJANGO_SECRET_KEY должен быть случайной длинной строкой.
# Для локального HTTP явно установите DJANGO_DEBUG=true в .env.
..\.venv\Scripts\python.exe manage.py migrate
..\.venv\Scripts\python.exe manage.py createsuperuser
..\.venv\Scripts\python.exe manage.py runserver 127.0.0.1:8000
```

Не перезаписывайте уже настроенный `.env`. Переменные окружения имеют приоритет
над `.env`. База PostgreSQL должна быть создана заранее; `migrate` создаёт таблицы.
SQLite fallback отсутствует. Секреты, данные PostgreSQL и `.env` исключены из Git.

API: <http://127.0.0.1:8000/api/>. Admin: <http://127.0.0.1:8000/admin/>.
Admin доступен только системным суперпользователям Django; учётная запись не создаётся автоматически.
Администратор организации — отдельная роль без `is_staff`/`is_superuser`, он работает через `/settings/users/`.

**Безопасность:** веб-интерфейс и API требуют авторизации и членства в организации.
Для публичного production отдельно настройте HTTPS, secure cookies, резервное копирование,
ограничение попыток входа и production WSGI/ASGI-сервер. `runserver` предназначен для разработки.
`DEBUG` по умолчанию выключен, в локальном `.env` включается явно.
Production-настройки, диагностические события, статика, условия доверия proxy и
план разрешённых отдельно проверок описаны в [этапе масштабирования 1](../docs/scaling-stage-1.md).

## Пользователи и организации

- `/register/` — создание новой организации и её первого администратора одной транзакцией.
- `/login/` — вход по логину и паролю; `/logout/` — выход только POST с CSRF.
- `/profile/` — имя, фамилия, email, текущая организация и роль.
- `/settings/users/` — список участников своей организации, создание аккаунта участника,
  изменение роли и удаление из организации; только администратор.
- Администратор, руководитель и менеджер имеют полный CRUD клиентов, сделок и задач
  своей организации. В v0.5 руководитель и менеджер имеют одинаковые CRM-права;
  управление участниками доступно только администратору.
- Один аккаунт состоит максимум в одной организации (`Membership.user` — OneToOne).
  Регистрация никогда не присоединяет к существующей организации по её имени или ID.
- Последнего активного администратора нельзя удалить или понизить через интерфейс.
  Изменения состава выполняются в транзакции с блокировкой организации.
- Удаление участника сохраняет его аккаунт и записи CRM, но немедленно закрывает доступ
  к CRM/API, в том числе в уже открытой сессии. Профиль и выход остаются доступны.
  Добавление через интерфейс создаёт новый аккаунт со свободным логином; повторное
  присоединение существующего аккаунта выполняет доверенный системный администратор.

После первого запуска откройте `/register/`. Системный `createsuperuser` сам по себе
не создаёт организацию и не даёт доступа к tenant API без членства.

### Обновление с v0.4

Сделайте резервную копию PostgreSQL и выполните `manage.py migrate`. Миграции добавляют
обязательную организацию каждой записи. Если существуют старые записи, они сохраняются
в отдельной организации «Данные до v0.5», включая UUID, даты и связи. Участники ей
не назначаются автоматически, поэтому первая регистрация не открывает доступ к старой базе.
Доверенный системный суперпользователь может через `/admin/` создать/выбрать аккаунт
и добавить ему Membership с ролью «Администратор» в эту организацию. Не переносите
отдельные связанные записи между организациями вручную. Для пустой базы архивная
организация не создаётся.

## Веб-интерфейс

- `/` перенаправляет на `/dashboard/` — статистика, последние сделки и ближайшие задачи.
- `/customers/` — клиенты и поиск.
- `/deals/` — сделки, поиск и фильтр стадии.
- `/tasks/` — задачи, поиск и фильтры статуса/приоритета.
- Создание: `/<раздел>/new/`; редактирование: `/<раздел>/<id>/edit/`;
  подтверждение удаления: `/<раздел>/<id>/delete/`.

Все формы валидируются на сервере. Удаление — только POST с CSRF-токеном.
Списки разбиты на страницы по 20 записей, фильтры сохраняются при переходах.
Статистика сроков использует настроенный Django TIME_ZONE (сейчас UTC).
Маршруты и поля REST API v0.3 сохранены; в v0.5 добавлены миграции организаций и проверка доступа.

Файлы интерфейса: `web/forms.py`, `web/views.py`, `web/urls.py`,
`web/templates/web/base.html` и остальные шаблоны страниц,
`web/static/web/style.css`, `web/static/web/app.js`. CSS адаптирован для телефонов,
на узких экранах широкие таблицы прокручиваются внутри своего блока.

Проверка веб-интерфейса и регрессии API:

```powershell
..\.venv\Scripts\python.exe manage.py test accounts web crmserver -v 2
```

## REST API

Используется сессионная авторизация Django: сначала войдите через `/login/`.
HTTP-клиент должен сохранять cookies; для POST/PUT/PATCH/DELETE передавайте CSRF-токен
в `X-CSRFToken`. Неавторизованный запрос или аккаунт без организации получает HTTP 403.
Все списки и поиск ограничены текущей организацией; чужой ID записи возвращает 404.
Чужие `customer_id`/`deal_id` отклоняются с 400, включая PATCH. Организация назначается
сервером, не принимается из JSON/формы и не может быть изменена клиентом API.

Одинаковые операции для `customers`, `deals`, `tasks`:

| Метод | URL | Операция |
|---|---|---|
| GET | `/api/customers/` | Список |
| POST | `/api/customers/` | Создать |
| GET | `/api/customers/{id}/` | Получить |
| PUT | `/api/customers/{id}/` | Обновить |
| PATCH | `/api/customers/{id}/` | Частично обновить |
| DELETE | `/api/customers/{id}/` | Удалить |

Вместо `customers` подставьте `deals` или `tasks`. Детальные URL используют числовой
серверный `id`. UUID уникален, создаётся сервером, возвращается в JSON и пока доступен
только для чтения, как `id`, `created_at`, `updated_at`. Сопоставление UUID при
синхронизации будет отдельным этапом; числовые ID разных устройств не совпадают.
Даты: `YYYY-MM-DD`; метки времени: ISO 8601, UTC. Суммы: десятичные строки с двумя знаками.

Списки имеют пагинацию по 50 записей: `count`, `next`, `previous`, `results`.
Поддерживается `?page=2` и поиск `?search=текст`.

Примеры POST JSON:

```json
{"name": "Демо-клиент", "company_name": "Демо-компания", "email": "anna@example.com"}
```

```json
{"title": "Поставка семян", "customer_id": 1, "amount": "125000.50", "stage": "Новая"}
```

```json
{"title": "Позвонить", "customer_id": 1, "deal_id": 1, "due_date": "2026-10-01", "priority": "Высокий", "status": "Новая"}
```

У задачи клиент, сделка и срок необязательны (`null` или отсутствуют). Если указаны
и клиент, и сделка, они должны соответствовать друг другу. Стадии, статусы и
приоритеты совпадают с desktop CRM. Сумма неотрицательная, по умолчанию `0.00`.
Имя клиента и названия сделки/задачи обязательны. Ошибки ввода возвращают HTTP 400.

При удалении клиента каскадом удаляются его сделки. Задачи остаются, ссылки на
удалённые записи очищаются. Записи удаляются физически, но приложение `synchronization`
сохраняет отметки с UUID/организацией/временем. Это работает для сайта, API и Django Admin.

## Desktop sync API

- `POST /api/sync/login/`: `username`, `password`; возвращает Bearer token, UUID и имя
  организации. Токен подписан сервером, действует 12 часов и проверяется на каждом
  запросе; удаление членства, смена организации/пароля и деактивация пользователя
  отзывают доступ. Вход ограничен 10 попытками в минуту на IP (локальный cache;
  для нескольких production workers нужен общий cache).
- `POST /api/sync/exchange/`: заголовок `Authorization: Bearer <token>`, JSON
  `organization` (UUID) и `changes` (полный снимок локальной базы, максимум 10 000).
  Каждая запись содержит `entity` (customers/deals/tasks), `uuid`, `updated_at`,
  `deleted`; живая запись также `created_at` и `fields`. Связи в `fields` передаются
  как `customer_uuid`/`deal_uuid`, а не локальные числовые ID.
- В sync API поле email необязательно и не проверяется как почтовый адрес для
  совместимости с desktop v0.1. Обычные веб-формы и REST API продолжают строгую проверку.
- Ответ: UUID организации, `synced_at` и полный объединённый `changes`, включая
  отметки удаления. Организация берётся из проверенного членства, UUID чужих записей
  и связей отклоняются. Обычный REST API сохраняет прежние числовые ID и session auth.
- Обмен — одна транзакция с блокировкой организации; обычные сохранения моделей и
  удаления используют ту же блокировку. Обновления моделей через произвольный ORM
  `QuerySet.update()`/сырой SQL обходят эти гарантии и не предназначены для обычной работы.
- Побеждает больший `updated_at`, при равенстве — сервер. Временные метки в UTC;
  смещение часов вперёд более 5 минут отклоняется. Удаления тоже версии, журнал пока
  хранится бессрочно. Каскад клиента сохраняется; живые сделки требуют живого клиента.
- `synchronization/tests.py` проверяет реальную desktop SQLite, HTTP, сайт и PostgreSQL.
  Выполните `manage.py migrate` и перезапустите сервер перед первым обменом.

## Файлы

- `crmserver/settings.py` — конфигурация, PostgreSQL и DRF.
- `crmserver/urls.py` — router API и Admin.
- `crmserver/models.py` — абстрактная модель UUID и временных меток.
- `accounts/models.py` — Organization и Membership с ролями.
- `accounts/access.py`, `permissions.py`, `api.py` — авторизация и ограничение данных организации.
- `accounts/services.py` — атомарная регистрация, добавление, смена роли и удаление участника.
- `accounts/forms.py`, `views.py`, `urls.py`, `templates/` — вход, регистрация, профиль, участники.
- `accounts/admin_site.py` — ограничение глобального Django Admin системными суперпользователями.
- `accounts/migrations/` и миграции сущностей — безопасный перенос старой базы и обязательный organization.
- `customers/`, `deals/`, `tasks/` — отдельные Django-приложения.
- В каждом приложении: `models.py`, `serializers.py`, `views.py`, `admin.py`,
  `apps.py`, `migrations/`.
- `crmserver/tests.py` — CRUD, валидация, связи, каскадное удаление, Admin.
- `.env.example` — пример конфигурации, `requirements.txt` — зависимости.

## Проверки

Из каталога `crmserver`:

```powershell
..\.venv\Scripts\python.exe manage.py check
..\.venv\Scripts\python.exe manage.py makemigrations --check --dry-run
..\.venv\Scripts\python.exe manage.py test accounts web crmserver -v 2
..\.venv\Scripts\python.exe tools\smoke_http.py
```

Тесты используют отдельную PostgreSQL-базу `test_<POSTGRES_DB>` и удаляют её после
завершения. Пользователю PostgreSQL нужны права на создание тестовой базы.
Desktop-тесты этими командами не запускаются.
`smoke_http.py` запускает `accounts.test_http`: настоящий HTTP-сервер на свободном
loopback-порту, регистрацию, сессионную авторизацию, CRUD и выход в отдельной тестовой
базе. Рабочая база не заполняется тестовыми аккаунтами. `accounts.test_migrations`
отдельно проверяет сохранность старых данных при обновлении.

## Необязательный отдельный локальный PostgreSQL

Если есть PostgreSQL 14+ с `initdb` и `pg_ctl`, но нет отдельной базы для разработки,
можно создать изолированный кластер CRM, не меняя установленные службы:

```powershell
..\.venv\Scripts\python.exe tools\local_postgres.py init --bin "C:\path\to\PostgreSQL\bin"
```

Команда создаёт `.postgres`, случайные пароли и `.env`, базу `crmserver`, слушает
только `127.0.0.1:55432`. Уже существующие `.env` и `.postgres` не перезаписывает.
Используется локальный PostgreSQL-пользователь с административными правами **только
для разработки**, не для production. Данные не находятся в базе другого приложения.

```powershell
..\.venv\Scripts\python.exe tools\local_postgres.py start
..\.venv\Scripts\python.exe tools\local_postgres.py stop
```

Это обычный локальный процесс, не служба Windows: после перезагрузки нужен `start`.
